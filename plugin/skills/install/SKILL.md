# install — one entry point, three surfaces, one checklist each

Beast is a protocol on GitHub objects (`docs/protocol.md`). What differs per surface is only HOW GitHub is reached and what can run. Detect the surface first, from evidence, and say which one and why before acting. Never guess, never run two sections. Every step below names its act, its gate and the evidence to quote: report each as `verified: <the line the gate printed>`, or as skipped, by name. A gate counts only after it has been run, never because it should pass.

## 0. Detect the surface

| Evidence | Surface |
|---|---|
| You have a Bash tool and `command -v claude` prints a path | **local** (terminal, or VS Code: one window with several repos) |
| You have a Bash tool; `gh api user -q .login` works; `gh api graphql -f query='{viewer{login}}'` is refused (`HTTP 403: GitHub GraphQL is not available from Claude Code sessions; use the REST API`), or `printenv GH_TOKEN` prints `proxy-injected` | **cloud** (GitHub through the sandbox proxy: REST only, attached repos only) |
| You have no Bash tool and your tool list has GitHub connector tools (search/list issues, get issue, create comment) | **cowork** (Cowork or Claude.ai chat: no shell; the GitHub MCP connector is the only GitHub) |

Anything else (a Bash tool but no `gh`; no Bash and no GitHub connector): stop and say what is missing; the fixes are below under the surface the person wants. Evidence: the command you ran and the line it printed.

## local — Claude Code on a machine (terminal or VS Code)

Run the steps in this order; each one's gate before the next.

1. **Tools.** Act: `command -v gh jq git python3`; `gh auth status`; the `project` scope only if workstreams will be opened (`gh auth refresh -s project`). Gate: four paths printed; `gh auth status` says `Logged in`. Evidence: the four paths and the login line.
2. **Marketplace install.** Act: `/plugin marketplace add DeSciX/DAITA`, then `/plugin install daita-beast@daita` (and `daita@daita`: the DeSciX connector is the `daita` plugin's job, `/daita:descix-setup`; never re-derive its setup here). If this session runs from `--plugin-dir`, offer the install and run it on the word. Gate, after the next session start: `claude plugin list` shows `daita-beast@daita` enabled at the version in `plugin/.claude-plugin/plugin.json` of `DeSciX/daita-beast` main (`gh api repos/DeSciX/daita-beast/contents/plugin/.claude-plugin/plugin.json -q .content | base64 -d | jq -r .version`), and the session's start context carries the `seat-hello` line (`scripts: <plugin dir>/scripts`, or, outside a coordinated repo, nothing until step 5). Evidence: the `claude plugin list` row, the version, the `scripts:` line.
3. **Permissions.** Act: `${CLAUDE_PLUGIN_ROOT}/scripts/permissions.sh <checkout>` prints the exact diff of `<checkout>/.claude/settings.json` (created if absent, every other key untouched) adding the `permissions.allow` rules a seat needs: `gh issue|api|search|project|label|pr`, `gh repo view`, and git's read verbs (`status log diff show rev-parse ls-files branch`, `worktree list`), each as `Bash(<prefix>:*)`; the plugin's own scripts need no rule, the PreToolUse hook `permit.sh` allows them (and the `cd <home> &&` prefix before them). Show the diff, ask, and only on yes run it again with `--write`, then commit `.claude/settings.json`. Gate: the second run prints `nothing to add: … already allows the 15 Beast rules`; a `gh issue list` in the next session runs without a prompt. Evidence: the `nothing to add` line and the commit sha.
4. **The plugin record.** Act: `source ${CLAUDE_PLUGIN_ROOT}/scripts/lib.sh && plugin_root_record "${CLAUDE_PLUGIN_ROOT}"` writes `~/.beast/plugin.json` `{"root", "version", "recorded_at"}` (the one writer; `plugin_root` is the one reader: `seat-hello`, `permit.sh`, `install-relay.sh` and the relay job consume it, so the committed CLAUDE.md block names no machine path). Rerun it after every plugin update, then steps 9 and 11 again (the watchdog re-points a mispointed relay by itself, never its own job). Gate: `jq -r .version ~/.beast/plugin.json` equals the installed version of step 2. Evidence: the line `plugin_root_record` printed.
5. **Repo.** Act: `${CLAUDE_PLUGIN_ROOT}/scripts/bootstrap.sh --repo <owner/repo> --path <checkout> --seat <LABEL> [--orchestrator <LABEL>] [--board <owner/repo>] [--token <SYMBOL> --community <owner/repo>]` (labels, templates, roster, the committed cloud pointer skill `.claude/skills/beast/SKILL.md`; `--token` and `--community`, which go together, only when the repo takes outside contributions: the token's symbol and the community repo that holds its `.beast/awarders.json`). Fill the roster (exactly one owner in `people[]`, `board`, `publishes_to` if there is a public twin), commit `.beast/`, `.github/ISSUE_TEMPLATE/`, `.claude/skills/beast/`. Gate: `${CLAUDE_PLUGIN_ROOT}/scripts/seats.sh list` prints the roster's seats with no prompt. Evidence: that list.
6. **Workstream.** Act: `/daita-beast:workstream` (`workstream.sh new`, with at least one milestone; it writes the empty `## Seats` table and names the master repo, the repo the tracking issue lives in). Gate: the tracking issue carries the labels `workstream` and `ws:<slug>`, and `workstream.sh seats <ref>` prints an empty table. Evidence: the issue url and the two labels.
7. **Seat.** Act: `/daita-beast:seat` scopes the seat with the person first, then runs `seat.sh new <LABEL> --repo-path <checkout> --agent <agent> --workstream <slug> [--kind …]` (the agent names a repo agent definition, `.claude/agents/<agent>.md` of the seat's repo, or the plugin's generic `daita-beast:seat`; the flags are the `seat` skill's, read it): one act writes the roster row, the home, the `## Seats` row and the master's CLAUDE.md block. Gate: `seat.sh where <LABEL>` prints the home and kind; `workstream.sh seats <ref>` shows the row. Evidence: both lines.
8. **Join.** Act: from any directory, `/daita-beast:join <LABEL>` (`join.sh <LABEL>`, which records the session's address from its Claude Code session file). Gate: its first line is `SEATED <id> at <home>`, and it ends by printing `resume.sh <LABEL>` and naming `<home>/CLAUDE.md` to read. Evidence: the `SEATED` line. From then on the home is the session's root: every shell command starts with `cd <home> &&`.
9. **Relay** (one per machine, for the coordinating checkout whose roster names every seat). The messenger must run in the SEATS' permission mode, because a receiver holds a message from a sender in another mode. Act: read `relay.permissionMode` from that roster; if absent ask once ("which permission mode do your seat sessions run in: default, acceptEdits, auto, bypassPermissions?"), write the answer into the roster as `"relay": {"permissionMode": "<mode>"}`, then `${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --repo <coordinating checkout> --permission-mode <mode>`. Gate: its `installed …` line names the mode and `relay <plugin dir>/scripts/relay.sh` (the path of step 4, never a checkout); `install-relay.sh --status` says installed. Evidence: both lines.
10. **Fixture.** Act: file a fixture (`decision.sh new --repo <repo> --assignee <login> --by <LABEL> --seat <LABEL> --title "FIXTURE install <UTC>" …`), wait two ticks (≤ 4 min): your own filing is never sent back to you, so `~/.beast/relay.log` says `own act, not sent: NEW <url>`. Then answer it as the decider, an untagged comment on the row (`gh issue comment <url> --body approve`). Gate: the `BEAST-EVENT kind=UPDATED` line arrives in this session; close it (`decision.sh close … --words approve --record <the comment url> --by <LABEL>`), and the log says `own act, not sent: DECIDED <url>`. Evidence: the UPDATED line and both log lines verbatim. No line in 4 min: `install-relay.sh --status`, then compare the mode in `~/.beast/relay.log` ("relay (haiku, <mode>)") with the seats' mode.
11. **Watchdog** (one per machine, beside the relay, for the same coordinating checkout). Act: `${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --job watchdog --repo <coordinating checkout> --permission-mode <the roster's relay.permissionMode>` (every 900 s; Haiku; the same mode as the relay, or its reminders are held). Gate: its `installed net.descix.daita-beast.watchdog …` line names `watchdog <plugin dir>/scripts/watchdog.sh`; within one tick `~/.beast/watchdog.log` carries a `tick:` line (`quiet …` with its call counts, or the signals it handed out); `install-relay.sh --job watchdog --status` says installed. Fixture: file `decision.sh new … --title "FIXTURE watchdog <UTC>"` for your own seated session, answer it as the decider (`gh issue comment <url> --body approve`), ack nothing for 15 minutes: a line opening `BEAST-WATCHDOG to=<your identity> check=unacked` arrives within the next tick; then ack and close the fixture. Evidence: the installed line, the `tick:` line and the reminder's first line.
12. **The decider's connector.** Act: hand the decider `docs/connector-access.md` if they answer from the Claude.ai board, and publish the board for them (`/daita-beast:board-ui`). Gate: they fetch one known private issue by number through the connector. Evidence: the issue title as the connector returned it.

**VS Code: one window with several repos.** A VS Code workspace (`*.code-workspace`) opens several repos in one window; every session starts in the folder the window was launched in (the launch folder) and its shell returns there after every command. Seating sets the root: `join.sh <LABEL>` from the launch folder finds the seat's home in any folder of the window, and from then on every shell command starts with `cd <home> &&` (or `git -C <home>`, absolute paths), every file edit uses an absolute path under the home, and `<home>/CLAUDE.md` is read at seating and after any compaction. Any number of seats share a launch folder or a window; two seats never share a home. At session start `seat-hello` lists the seats of every folder of the workspace files that list the launch folder (found walking up from it to `$HOME`, in any position), each with its `join.sh`, and claims none. Steps 3 (permissions) and 5 (bootstrap) run once per repo; steps 2, 4, 9 and 11 once per machine.

## cloud — Claude Code in the cloud

Plugins are not installed in a cloud session; a committed skill is. The repo must carry `.claude/skills/beast/SKILL.md` (written by local step 5 on a machine and committed). If you are reading this skill in a cloud session, that pointer brought you here.

1. **Clone.** Act: `git clone --depth 1 https://github.com/DeSciX/daita-beast "$HOME/daita-beast"` (or `git -C "$HOME/daita-beast" pull`). Gate: `ls "$HOME/daita-beast/plugin/scripts"` lists the scripts; each verb's text is at `$HOME/daita-beast/plugin/skills/<verb>/SKILL.md`. Evidence: the listing's first line.
2. **Every wake.** Act: `decision.sh inbox <LABEL>` (computed from acks on GitHub, identical on every machine), act, `ack.sh` each row, then `resume.sh <LABEL>`. Nothing on this surface can message out to a local seat and nothing is pushed in: the inbox at each wake is the whole hearing. Gate: the inbox prints, with `0 rows` or the rows. Evidence: its header line.
3. **Limits, stated, never worked around.** GraphQL is blocked, so GitHub Projects verbs refuse by name and board pinning degrades to a warning; only repositories attached to the session are reachable (`add_repo {owner, repo, access:"push"}` attaches one when the session has that tool; org-level API paths are refused; otherwise a decision for an unattached repo is one line to a local seat, who files it); the proxy appends a `_Generated by Claude Code_` footer to issue bodies it creates, which lands inside the last section (`## Record`): say so in the row rather than editing it out; the relay never runs here. Evidence for the surface: the GraphQL refusal line of step 0.
4. **Setup script.** The repo's cloud environment setup script may carry the clone line so step 1 is automatic; that file is the owner's: offer the line, never write it unasked.

## cowork — Cowork or Claude.ai chat

No shell: the protocol runs as GitHub connector calls; the recipes are `/daita-beast:connector`. Cowork hears nothing pushed and runs no script: its refresh is a scheduled task.

1. **Install.** Act: Customize › Plugins › Add marketplace `DeSciX/DAITA` › install `daita-beast` (and `daita` for the DeSciX connector). Gate: `/daita-beast:connector` loads. Evidence: its first heading.
2. **Access.** Act: `/daita-beast:connector` step 0 (tools, access, roster, write guard): it fetches one known private issue by number through the connector, which proves access, not query. Gate: the issue comes back by title; denied or not found means the GitHub app is not installed on that account (`docs/connector-access.md` names the fix: once per organization and once on the personal account, each with its repository list). Evidence: the title the connector returned. Run no other recipe before this gate.
3. **Board page.** Act: `/daita-beast:board-ui` publishes the decider's board artifact (the template is in the plugin; the connector's display name `github` is a constant in it, so a differently named connector is reported, never patched in the session). Gate: the page lists the open rows the connector lists. Evidence: the artifact url and one row title.
4. **Scheduled tick.** Act: create a Cowork scheduled task whose prompt is exactly `/daita-beast:cowork-tick <owner/repo>`, `<owner/repo>` the roster's home repo (Cowork has no checkout to find a roster in; the skill refuses without the argument), on a schedule of 15 minutes or more (a tick's one large read is the artifact, plus its searches). Gate: the first run posts the decider's digest, or says the tick was quiet. Evidence: the task's prompt line and the first run's output.
5. **A seat here.** Its inbox is the connector inbox recipe at each wake (computed from acks, nothing local), and it acks by the connector ack recipe.

## Always

Report what was measured, not what should work: the command, the line it printed. A step that was skipped is named as skipped. Nothing here reads DeSciX platform source; the DeSciX side is the `daita` plugin and the published CLI.
