# The Beast protocol

Beast is how agent teams coordinate work on DeSciX using GitHub's own objects. It adds guidelines and a thin plugin, nothing else: GitHub keeps the permissions, the history and the cost. Any team can run it under its own owner; a dependency on the platform is an issue filed in the platform's repo.

## The mapping

| Beast concept | GitHub object | Where it lives |
|---|---|---|
| Workstream (id: a slug) | one Projects v2 board plus one tracking issue labelled `workstream` and `ws:<slug>`; exactly one open issue carries both among the workstream owners (the roster's owners plus its `workstream_owners`; `workstream_issue <slug>`); nothing stores its number | the Project under the owner that coordinates it; the tracking issue in the **master** repo (the master is the issue's repo, derived) |
| Which seats are in a workstream, with repo, home and agent | the `## Seats` table of the tracking issue (`| Seat | Repo | Home | Agent | Account | Address | Seen |`, the first four cells the definition, the last three rendered), parsed by one parser and written by one renderer (`ws_seats_parse`, `ws_seats_write`; `workstream.sh seat-add|seat-remove`) | the tracking issue; rendered copies: the master's CLAUDE.md block (`workstream.sh render`), every home's Beast block, `seats.sh list` |
| A seat's role | an agent file: `<repo>/.claude/agents/<name>.md` (the roster row's `agent`), or the plugin's generic `daita-beast:seat` (`plugin/agents/seat.md`), which a repo agent specializes with its domain and the line `Seat role: daita-beast:seat` | the seat's repo; the plugin |
| Public description of a workstream | the Project README and the tracking issue body (northstar verbatim, repos, acceptance, seats) | the Project |
| Details and status reports | comments on the tracking issue, fixed `BEAST-STATUS` header | the coordinating repo |
| Pending decision (an act without code) | an issue labelled `decision`, assigned to the person whose word it needs, six fixed sections | the filing seat's home repo (the roster `repo`, always private); the repo it decides, when another, is a `Decides:` link at the end of its Decision section; added to the workstream's Project |
| Pull request for the decider's review | the PR itself, labelled `needs-review` and `seat:<login>/<LABEL>`, assigned to the decider (`pr.sh request`) | the PR's repo, when it is private |
| A decider's board | the search `is:open label:decision,needs-review assignee:<login>` (issues and PRs) and a generated issue pinned in the coordinating repo: the pending table and the decided table (last 7 days, with the words) | GitHub; nothing hosted |
| A seat's desk (questions across the desk, messages) | one long-lived issue per seat, `Desk: <login>/<LABEL>`, labelled `desk` and `seat:<login>/<LABEL>`, assigned to the decider; asks, answers and messages are its comments, its body is generated (`desk.sh`) | the seat's own repo (`seat_repo`: this roster's row, else the Repo cell of its `## Seats` row) |
| An act only the assignee can do (public flip, chain, secret, scope grant) | `decision` plus the `hands` label | same |
| Cross-repo dependency | an issue filed in the target repo, added to the dependent Project | the target repo |
| A ruling, verbatim | the decider's answer comment on the row, or the words typed to a session quoted verbatim in the row's close comment; kept until the milestone's wrap-up folds them into the docs and deletes the row | the row's repo |
| Seat roster (this repo's own seats: login, label, agent, workstream, home, optional lane) | `.beast/roster.json`, committed; every row's `repo` is the roster's own (a peer row is refused: peers live on the workstream issue) | each coordinating repo, always a private one |
| Milestone (a dated deliverable a seat schedules) | a GitHub milestone: title, due date (GitHub's `due_on`), description of fixed lines (`milestone.sh`) | the repo its items live in; a seat's are on its home (the roster `repo`) |
| Dependency (what a seat waits on) | one line `Waits on: <seat id \| owner/repo#N>`, in a row's `## Waits`, an ask's lines or a milestone's description; measured by `deps.sh` | where it is declared |
| Twin (a public product's private repo) | the roster's `repo`, with `publishes_to` naming the public repo | the roster |
| Milestone wrap-up (release notes, fold-in, clean-out) | a plan file `.beast/wrapup/<slug>/plan.json` committed in the repo, one decision row `Decision: Wrap up <M>` approving it, a GitHub Release on the public repo (`wrapup.sh`) | the repo the milestone is on; the release on `publishes_to` |
| A seat's durable notes (what it must not relearn) | one comment `BEAST-NOTES seat=<login>/<LABEL>` on the seat's tracking issue, edited in place | the tracking issue's repo |
| A machine watchdog's learnings | one comment `BEAST-WATCHDOG-NOTES machine=<hostname> at=<UTC> entries=<n>` on the Beast workstream's tracking issue, edited in place by `watchdog.sh`; its ledgers and offsets in `~/.beast/watchdog/state.json`, a cache | the plugin twin; the machine |
| A seat's home (the directory its sessions run in) | the roster row's `home` (`kind`, `branch`; `kind`, `dir` for a subdir); the local path is derived, and the home carries a machine-local `.beast/seat.json` | the roster; the machine |
| A seat's address and Claude account | one comment `BEAST-ADDRESS seat=<slug>/<LABEL>/<login> account=<claude account> address="<name>[ [ref]]" machine=<hostname> at=<UTC>` by the seat on its tracking issue, edited in place (`seats.sh record`, which `join.sh` runs with the session's live name; the machine watchdog's tick re-stamps the address and `at=` with `seats.sh touch` from the live name of the seat's claimed session); the session's name is read from Claude Code's session file `~/.claude/sessions/<pid>.json` (`lib.sh::claude_session_of`, the one reader); `~/.beast/sessions.json` is a machine-local cache of it, keyed by the identity only (`sessions_key_check` refuses any other key before a write; `seats.sh` drops a key of another shape at every run, naming it) | the tracking issue's repo; the machine |
| Which session holds a seat on this machine | the session claim in the seat's `~/.beast/sessions.json` entry: `session`, `session_at`, `launch`, `tracking`, `ended_at`, `previous` (`lib.sh::sessions_claim`, written by `join.sh` and `seats.sh record` from `$CLAUDE_CODE_SESSION_ID`; `sessions_end`, written by the SessionEnd hook) | the machine |
| Hand-back | a pull request whose description carries the evidence section below | the repo |
| Token authority (which repos may award a token) | `.beast/awarders.json` `{"token": "<SYMBOL>", "awarders": ["<owner/repo>", …]}`, read through GitHub at its default branch (`community_awarders`) | the token's community repo, named by each award policy's `Community:` line |
| Award ledger (a month's awards of a community) | `awards/<YYYY-MM>.jsonl` and `.md`, generated by `ledger.sh` from the `BEAST-AWARD` comments, never edited | the community repo, committed by its owner |

A Project can hold issues and pull requests from repositories under other owners (measured 2026-10-10: an issue of a repository under one owner added to a Project of another owner and read back). Linking a Project to a repository's sidebar is same-owner only and is cosmetic.

## Shapes

**Decision issue** (template `.github/ISSUE_TEMPLATE/decision.md`): title `Decision: <plain question>`; sections `## Decision`, `## Unblocks`, `## Waits`, `## Recommendation`, `## Approve with`, `## Record`. Every section non-empty. `decision.sh new --decides <owner/repo>` appends the line `Decides: https://github.com/<owner/repo>` to `## Decision` when the decided repo is not the one the row is filed in; there is no seventh section. A row is filed under a milestone (`--milestone`, below); each `--waits-on <ref>` appends `Waits on: <ref>` to `## Waits`. `Approve with` holds the exact phrase, one per row: `decision.sh new` refuses a phrase carrying `|` (a choice between options is a desk ask, `desk.sh ask --options`); any other wording from the decider is a question back. `decision.sh new` (and so `record`) reuses an OPEN `decision` issue of the repo with the identical title and the same `seat:` labels filed by the same login instead of filing a second, and returns only once the issues list shows the row it filed, so a rerun after a failure part-way never duplicates. `Record` cites where the words will be: the decider's answer comment, or a file committed in the repo; the close comment quotes the words verbatim. The board renderer parses these sections by shape and fails loudly on a body that lacks one.

**Workstream tracking issue** (template `workstream.md`): labels `workstream` and `ws:<slug>`; title `WS: <name>`; sections `## Northstar` (the definer's words, verbatim), `## Project`, `## Master repo` (the issue's own repo, named), `## Repos involved`, `## Acceptance`, `## Milestones`, `## Seats`. The `## Seats` section is one table, parsed by shape (`ws_seats_parse`, lib.sh: a missing or other header, a row that is not exactly 7 cells, a Seat that is not `<login>/<LABEL>`, a Repo that is not `owner/repo`, a Home outside the vocabulary, an Agent that is not an agent name, or a duplicate seat dies naming the line):
```
| Seat | Repo | Home | Agent | Account | Address | Seen |
|---|---|---|---|---|---|---|
| octocat/BUILDER | acme/widgets-dev | worktree seat/BUILDER | builder | octocat@example.com | widgets-3a [18decb] | 2026-10-19T10:00:00Z |
```
Seat is the short id (the slug is the issue's); Repo is private and not public-intended; Home is `checkout`, `worktree <branch>`, `wrapper` or `subdir <dir>` (`seat_home_path_of`'s vocabulary); Agent is the agent name. Account, Address and Seen are rendered by `ws_seats_render` from the seats' `BEAST-ADDRESS` comments on the same issue and ignored by the parser: a hand edit of an address in the table edits nothing.

**Address** (one comment per seat on its tracking issue, by the seat's login, edited in place by `seats.sh record` and `seats.sh touch`):
```
BEAST-ADDRESS seat=<slug>/<LABEL>/<login> account=<claude account> address="<name>[ [ref]]" machine=<hostname> at=<UTC>
```
The address is the session's ListAgents name, optionally followed by the 6-hex `[ref]` ListAgents prints (`lib.sh::ADDRESS_RE`, the one owner of the shape; `address_parse`). The name is the `name` field of the session's `~/.claude/sessions/<pid>.json`, which carries no ref, so `join.sh` and the watchdog record a bare name. A name holds no bracket, double quote or control character. SendMessage is sent to the bare name (the relay strips a recorded ref); a name that two live sessions on the machine carry is recorded, and `seats.sh` prints `ambiguous: <n> live sessions on this machine are named "<name>"`.

**Seat-to-seat line** (the first line of a direct `SendMessage` from one seat to another, and of the durable copy `desk.sh msg` writes on the recipient's desk; `MSG_HEADER_RE` in lib.sh, the page's `MSG_RE` its twin):
```
BEAST-MSG from=<slug>/<LABEL>/<login> to=<slug>/<LABEL>/<login> re=<owner/repo#N | url | none> blocking=no at=<UTC>

<the body>
```
It never names the decider's board, never waits on the decider and is never shown on the board; a seat that needs his word files a row.

**Status report** (a comment on the tracking issue):
```
BEAST-STATUS seat=<login>/<LABEL> at=<UTC> state=working|blocked|done|handoff next=<the next critical-path act and when it is measured>

<evidence: what ran, exit codes, hashes, links to issues, PRs and records>
```
Posted at a blocker, a completion or a seam, and as a `handoff` before a compaction or a shutdown (read back by `resume.sh`). Never a tick. A blocked report names the decision issue or the cross-repo issue it waits on.

**Ack** (a comment on a board row or a desk, one per seat per event):
```
BEAST-ACK seat=<login>/<LABEL> at=<UTC> state=seen|executed|blocked next=<the act and when it is measured>

<evidence or the blocker, optional>
```

**Hand-back** (a pull request description):
```
## What
## Evidence
<what ran and its exit code; served==built hashes where a deploy is involved; the negative control that failed before the fix>
## Review against the engineering rules
<the builder's own diff review: one owner per fact, no compat fences, fail loud, no hardcoded fallbacks>
## Closes
<issues this PR closes, decisions it consumed by number>
```
A PR without the evidence section is not hand-back ready.

**Roster** (`.beast/roster.json`): `repo` (private, never public-intended), `publishes_to` (optional: the public repo this repo is the private twin of; public on GitHub or public-intended), `public_intended` (optional: owners or `owner/repo`s that are public or will be; compared case-insensitively), `scrub` (optional: patterns the publish scrub gate refuses, besides its fixed classes: a regex string, applied to every text file, path name, commit message and body, or `{"pattern": "<regex>", "paths": ["<glob>", …]}`, applied only to text files and path names whose path matches a glob, Python `fnmatch` on the whole path with `*` crossing `/`), `scrub_allow` (optional: private repos' bare names that are also ordinary words; the bare-name class skips exactly those, their `owner/repo` is still refused; `scrub_allow_words` (optional: phrases of closed-row words that may publish, each one line of one word or more; the words class applies them as Publishing says), `roster_scrub` in `lib.sh` parses the three fields and dies naming a malformed entry), `vendored` (optional: directories, plain paths relative to a repo's root, holding byte-exact copies of upstream packages; the license check skips their manifests and the scrub skips its private-repo, private-name, words and roster-scrub classes on their files; `roster_vendored` in `lib.sh` is the one parser and dies naming a malformed or repeated entry), `license` (optional: the license every public repo of the roster's owners carries; its shape under License below), `workstream_owners` (optional: GitHub owners, beyond the ones the roster names in `repo`, `board` and `seats[].repo`, whose `workstream` + `ws:<slug>` tracking issues this repo's seats may join, e.g. `["threejs"]`; an owner not listed is never searched for a workstream; `roster_workstream_owners` in `lib.sh` is the one parser and dies naming the field on anything but a list of owner names, an entry listed twice, or one the roster already names), `coordinates` (one line), `seats[]` (`label`, `github`, `repo`, `agent`, `workstream`, `home`, optional `lane` and `retired`; `lane` is the repo CLAUDE.md's `LANE: <name>` line when it has one (a repo without one records no lane, and `seat.sh new` says so; no script reads it to decide anything), and a `lane` present that is not a name (a-z, 0-9, -) is refused; `repo` equals the roster's own `repo` (a row naming another repo is a peer row and is refused: peers live on the workstream issue's `## Seats` table); `agent` is the role, `<name>` for `<repo>/.claude/agents/<name>.md` or `daita-beast:seat`; `workstream` is the slug whose tracking issue carries the labels `workstream` and `ws:<slug>`; the pair `github`/`label` is unique and `<workstream>/<label>/<github>` is the seat's identity, derived, never stored; `home` is `{"kind": "checkout|worktree|wrapper", "branch": "<branch>" | null}` or `{"kind": "subdir", "dir": "<path relative to the checkout>"}`; `retired` is a date `YYYY-MM-DD`; a row carrying `role` or `tracking` is refused naming the key: `roster_check_unique` in `lib.sh` is the one check), `people[]` (`github`, `name`, `role`). Every home of a repo (its checkout, worktrees and wrappers) reads the main checkout's roster. The scripts read the roster from the repo's main checkout, never a worktree; try a roster change in a clone of the repo.

**Seat notes** (one comment on the seat's tracking issue, by the seat's login, edited in place by `notes.sh`):
```
BEAST-NOTES seat=<login>/<LABEL>
<one fact per line: where the home is, standing constraints, anything the seat must not relearn on another surface>
```
Two such comments for one seat are a defect: `notes.sh` names both and refuses to choose.

**Watchdog lines** (`watchdog.sh`, the machine watchdog; bookkeeping, never an event or a desk message, and a stray one on a desk is dropped and named by `desk_parse`):
```
BEAST-WATCHDOG to=<identity> check=<id> at=<UTC>                 the first line of a reminder it sends a live seat by SendMessage
BEAST-WATCHDOG machine=<hostname> at=<UTC> check=<id>            the first line of a bug it files on the plugin twin, and of a recurrence comment there
BEAST-WATCHDOG-NOTES machine=<hostname> at=<UTC> entries=<n>      its one notes comment per machine on the Beast tracking issue
<date> GOTCHA|FALSE|TUNE <check> <object> — <one line>           a notes entry, newest first
```
A seat acts on a reminder and never replies to it or relays it.

## Seats and messages

A seat is an identity: one role (an agent file) held by one GitHub login under a label in one workstream. Its identity is `<slug>/<LABEL>/<login>` (for example `widgets/BUILDER/octocat`): the key of the seat map, of `seats.sh list`, of `~/.beast/sessions.json` and of the `BEAST-ADDRESS` comment. Inside one workstream's own artifacts (row labels `seat:<login>/<LABEL>`, acks, status headers, close comments, event lines, the `## Seats` table) the short id `<login>/<LABEL>` abbreviates it, resolved through the roster row's `workstream`. A label is unique per login, so two users may each hold a BUILDER and one user may hold several seats in one repo; the same login and label in two workstreams are two identities. The roster row carries `github`, `label` and `workstream`; the identity is derived from them and never stored. Every script that takes a seat accepts a LABEL, `login/LABEL` or the identity: a bare LABEL resolves through this repo's roster, then through every open workstream's `## Seats` table (`ws_seats_all`), to exactly one seat, and is refused otherwise naming the candidates' identities. A verb acting AS a seat (`desk.sh open`, `ask`, `withdraw`, `publish`, `inbox` and `msg --from`; `ack.sh`, `notes.sh`, `deps.sh`, `decision.sh inbox`) resolves it through this repo's roster only (`seat_rostered`, no network). A verb naming ANOTHER seat (`desk.sh msg <TO-SEAT>`, `desk.sh answer <SEAT>`, `--waits-on` and every `Waits on: <seat>` ref `dep_state` measures) resolves it through this roster, then the workstream tables (`seat_id`), and acts in that seat's own repo: `seat_repo` is the one owner of which repo holds a seat's desk and milestones (this roster's row when the seat is rostered here, else the Repo cell of its row in its workstream's `## Seats` table, `ws_seats_all`), and `desk_find <id> <repo>` reads the desk there. Displays shorten an id to its LABEL when the login is the viewer's own. Every row label is qualified (`relabel.sh --apply` qualifies bare ones). Comments written before a relabel can carry a bare `seat=<LABEL>` ack or status header or `Closed by seat <LABEL>`; those are read as the seat the label resolves to uniquely through the reading checkout's roster, and a bare label that does not resolve is named and dropped. A session holds a seat. Its first act is `/daita-beast:join <LABEL>`, which reads its own address from `ListAgents` and records it: the seat's `BEAST-ADDRESS` comment on its tracking issue (address, Claude account, `oauthAccount.emailAddress` of `~/.claude.json`, machine, time; one comment, edited in place), the machine-local cache and the rendered cells of the `## Seats` table. Addresses change on every reload and are verified by a reply before anything is relied on. Inter-seat traffic is at a seam, a blocker or a completion, nothing else: `seats.sh address <SEAT>` reads the comment live and says which path applies, **direct** (`SendMessage`, only when both seats run as the same Claude account on the same machine and the address was recorded within 24h, an approximation of "after the recipient's newest session start"; the line opens with the seat-to-seat tag above) or **desk** (`desk.sh msg`, the durable copy on the recipient's desk, read at its next wake); a cross-repo ask is an issue in the target repo. A human's words are relayed verbatim and labelled as theirs, never paraphrased.

## Two tiers: the board and the desks

The test: **would a development team put this on a PR or an issue for the lead's approval?** Yes: it goes on the **board**, as a pull request awaiting the decider's review (a code change) or a `decision` issue (an act without code: deploy PROD, release, spend, chain, secrets, scope, a design approval, ship-or-cut). No, it is a question you would ask the developer across the desk (what to name something, a rewording, which of two options, "did you mean"): it goes on the seat's **desk**, which never touches the board. An ask that turns out big is filed as a decision or a PR, and the ask is answered `→ <row url>`. Neither tier carries words the decider already gave in a session that need no explanatory content.

| | Board | Desk (one per seat) |
|---|---|---|
| holds | PRs for the decider's review; `decision` issues | asks (naming, wording, an option, a clarification); messages from seats or the decider |
| GitHub object | the PR (labels `needs-review` + `seat:<id>`, assignee the decider) or the `decision` issue | ONE issue per seat in its own repo (`seat_repo`), labels `desk` + `seat:<id>`, assignee the decider |
| answered by | an assignee comment in one of the answer forms (below) | `BEAST-ANSWER n=<n> <option or text>` on the desk |
| record | the answer comment URL | the answer comment URL |
| visible on | the generated board and the board page | the desk's generated body; never in the board tables |
| written by | `pr.sh request`, `pr.sh close`; `decision.sh new`, `close`, `record` | `desk.sh open`, `ask`, `answer`, `withdraw`, `msg`, `publish` |
| read by | `board.sh`, `decision.sh inbox`, the relay | `desk.sh inbox` (and so `decision.sh inbox`), the relay |

**A PR on the board.** Every seat posts as the decider's login today, and GitHub refuses a review request to, or an approval by, a PR's own author, and does not notify a user of their own @mention. So `pr.sh request <pr> --seat <id> --unblocks "<text>" --recommendation "<text>"` writes the two texts into the PR body as its `## Unblocks` and `## Recommendation` sections (`PR_ROW_SECTIONS` in `lib.sh`, through `section_replace`; a rerun replaces them), then labels the PR `needs-review` and `seat:<id>` (read back after the write, `seat_labels_require`: a label that did not land fails the request, naming it) and assigns the decider (the roster's `people[]` row whose role names "owner"; it dies when there is not exactly one, and `--assignee` names another). Both texts are required: missing, empty, or pointing elsewhere for their substance (`ask_inline_check`), the request is refused before any write. The board shows them on the PR's row as on a decision row (`board.sh` and the board page read them by shape; a needs-review PR without them fails `board.sh`, naming it, and shows as malformed on the page). The PR's approving phrase is the first quoted phrase of a `## Approve with` section of its body, else `approve`; the decider answers with the decision forms (the phrase, `<phrase> — <comment>`, bare `approve`/`approved`, `revise: …`, `reject: …`). On approve the hearing seat runs `pr.sh close <pr> --merge --words … --record <answer url> --by <id>`: it merges (REST `PUT pulls/{n}/merge`) and dies naming GitHub's refusal (a conflict, a failing check) without commenting or closing; on reject `--rejected` closes it unmerged with the label `rejected`. Both write the same close comment as `decision.sh close` (one writer, `row_close_comment` in `lib.sh`), republish the board and print the row's seats.

**The desk.** `desk.sh open <id>` creates it once (`seat.sh new` runs it, so a new seat can be asked from its first session): it finds the desk by its labels through the issues list and dies when there are two. The issues list lags a create by seconds (measured 2026-10-15: a second `open` one second after the first minted a duplicate), so `open` returns only once the list shows the new desk; two `open`s of one seat run concurrently are not guarded. Comments, one fact each:
```
BEAST-ASK n=<seq> seat=<login>/<LABEL> at=<UTC> milestone="<title>"   desk.sh ask; n = the highest n on the desk + 1;
                                                     the milestone field is required while the desk's repo has an open
                                                     milestone, and an ask written before milestones has none
<the question, one or two lines>
options: a | b | c                                   optional
default: a                                           optional: what the seat does if no answer by its next seam
Waits on: <seat id | owner/repo#N>                   optional, one per dependency

BEAST-ANSWER n=<seq> <option or free text>           by an assignee of the desk, or posted by desk.sh answer, which adds
(words typed to <login>/<LABEL>'s session, verbatim)  this line when the decider typed the words to the seat's session

BEAST-WITHDRAW n=<seq>                               desk.sh withdraw: the seat withdraws its own open ask

BEAST-MSG from=<slug>/<LABEL>/<login> to=<slug>/<LABEL>/<login> re=<ref|none> blocking=no at=<UTC>
<the body>                                           desk.sh msg, on the recipient's desk: the seat-to-seat line (Shapes)
```
A plain comment by an assignee is a message from the decider. An answer or withdrawal of no open ask, an ask or message for another seat, a malformed `BEAST-` line, and a plain comment by anyone else are named on stderr and dropped. A `BEAST-MSG` line that is not the shape (a pre-1.5.0 `from=<login>/<LABEL> to=<login>/<LABEL> at=<UTC>` tag) is dropped loud only inside the seat's inbox window, newer than its last ack on the desk (`seat_acks`); older ones are history the seat acted on, counted once in one stderr line, `<n> pre-1.5.0 message line(s) older than the last ack (<ack>): history, not read`, never listed (`desk_parse`). With no ack every comment is in the window. The body is a view regenerated from the comments by `desk.sh publish` (every desk write publishes): a header line, "Open asks" (n, the question's first line, options, default, link), "Answered (last 20)" (withdrawn asks included), "Messages (last 10)". Nobody edits it, and the desk is never closed. The seat acks on its desk like on a row (`ack.sh <desk> --seat <id> --state seen --next …`); its desk inbox (`desk.sh inbox <id>`, printed at the end of `decision.sh inbox`) is every answer and every message newer than that ack.

## The board is a queue

Every board item (a decision, or a PR for review) is a message on the board before anyone acts on it, and nothing on the board's side of the test is decided off it. A seat enqueues (`decision.sh new`), the decider answers, the hearing seat closes on the words with the record. Anything a seat waits on from the decider is filed with `decision.sh new` before it is asked, and stays open until the word. `decision.sh record` (file and close in one act) is only for a significant word the decider already gave in a session before any row existed (scope, engine, ship-or-cut, release: anything that needs explanatory content), so it passes through the queue like every other; it is never used for a question the seat is about to ask, which leaves nothing pending on the board; a minor word (wording, copy, a link) is recorded verbatim in the repo's dated record with no row. The consumed log is the board's decided table (closed rows of the last 7 days with their words); the row keeps the words until its milestone's wrap-up folds them into the docs.

One check holds it: `decision.sh new` (and so `record`) and `desk.sh ask` refuse a question that points elsewhere for its substance, "see session", "see my session", "as discussed", "per our chat" or a local path (`/Users/…`, `/home/…`, `~/…`), before anything is written, naming the rule: the content inline, or a URL to a file or diff at a commit (`ask_inline_check` in `lib.sh`).

A row (a decision issue or a PR labelled `needs-review`) has the same queue mechanics. A row's **seats** are its `seat:<login>/<LABEL>` labels: every seat the decision affects, always including the seat that filed it (`decision.sh new` labels `--by` beside every `--seat`, `pr.sh request` its `--seat`, and both read the labels back and fail naming one that did not land). A row with no `seat:` label at all (filed before the filer was always labelled) has one seat, its filer, the seat of its first `BEAST-ACK` comment, and none when it has no such comment (`row_seats` in `lib.sh`, the one owner read by `board.sh`, `watch.sh` and the close's list of seats to tell; the board page's `rowSeats` is its twin). `decision.sh inbox` finds rows by their seat label, so a row with none is not in it. Its **latest event** is the newest of its creation, the decider's newest answer-form comment, and its close. Each seat **acks** for itself with one comment, `BEAST-ACK seat=<login>/<LABEL> at=<UTC> state=seen|executed|blocked next=<act>` (evidence below); a close by a seat is that seat's seen ack at the close (the close comment names its closer), and the seat that files a row acks it seen as the row's first comment (`decision.sh new --by <SEAT>`, `pr.sh request --seat <SEAT>`), so its own filing never sits in its inbox. A seat's own comment on a row is tagged: an `ack.sh` comment, whose `--text` carries a reply or evidence, or a comment whose last line is the seat's `BEAST-ACK`; an untagged comment is attributed to the decider (the relay's actors of an event, `event_actors`). Attribution is not an answer: a row leaves the decider's turn only on an assignee's comment in an answer form (below; `answer_kind`, `row_answer_url`), or its close. A seat is **current** on a row when its newest ack is at or after the latest event, otherwise the row is in its **inbox**; a row is **consumed** when every seat is current after its close. The inbox is computed from GitHub alone (`decision.sh inbox`, or the connector recipe), so a seat on any machine or surface gets the same one; nothing is held locally. Delivery is at-least-once: the relay pushes an event line where a machine runs one (an optimization, never the contract), the inbox is the pull, a seat de-duplicates by issue URL, and the relay never sends a seat its own act (below). A `revise:` is a new event for every seat. A row closed by mistake is reopened with a comment saying so; the close is withdrawn, never rewritten.

A row's body changes only through `decision.sh revise` (after the decider's `revise:`), `pr.sh request` (a rerun replaces its sections), `publish.sh request --amend`, or `decision.sh restore <row> --by <SEAT>` by its seat; a hand edit of the body is not a path. Every script that writes a row's body records it on the comment it posts right after, as that comment's last line `BEAST-BODY digest=<digest>` (`lib.sh::body_line`: `decision.sh new`'s filer ack, `revise`'s and `restore`'s amend comment, `pr.sh request`'s requester ack; `publish.sh request` files through `new`). `restore` is how a seat repairs a body broken by a hand edit without the decider: it is refused unless `--by` is the row's filer (`row_filer`) or one of its seats (`row_seats`); it takes the newest body line on the row (`body_record_last`), finds the version of the body with that digest in the issue's edit history (GraphQL `userContentEdits`, `issue_body_versions`) and writes it back byte for byte, never composing text; and it posts one comment whose first line is the amend line `Amended at <UTC>: restored the body recorded at <comment url>; changed: <sections>`, so an approval older than it no longer counts. It refuses a closed row, a row whose decider's `revise:` is pending (`decision.sh revise` answers that), a row with no body line (filed before the line existed, or from a surface without a shell), a body that already is the recorded one, an edit history it cannot read or that lacks the recorded body, and a recorded body that is itself malformed (`section_required`).

## Decisions

Decisions are repo- and project-specific, never Beast-wide. The seat that is blocked files the decision (`/daita-beast:decision`) BEFORE it asks the decider, in its home repo: `decision.sh new` files in the roster's `repo` unless `--repo` names another private repo, and `--decides <owner/repo>` names the repo the row decides (an app's decision names that app's repo, a platform decision the platform repo). A decider's board spans every repo they are assigned in and is published in one place (the roster's `board` repo), but a decision made on it is a rule only inside the repo it decides. A row is built from the current end of the record it cites, re-read at filing time, never from an earlier snapshot. It is assigned to the decider, carries a `seat:<login>/<LABEL>` label for every seat that waits on it, and is added to the workstream's Project.

The decider answers in either of two ways, and both are records: a comment on the issue in their own words (the comment URL is the record; GitHub stamps author and time), or the words typed to a session, which that session quotes verbatim in the close comment. The close comment quotes the words and cites the record. Four answers exist: **approve** (the issue's exact phrase; on the issue itself a bare `approve` or `approved` from the assignee counts the same, since the assignee and the issue are unambiguous there, while words typed to a session need the phrase to name the decision), **approve with comment** (`<phrase> — <comment>`, approves and shapes the act), **revise** (`revise: <what to change>`, not an approval: the seat revises the row itself with `decision.sh revise`, which rewrites only the named body sections and posts one comment whose first line is the amend line `Amended at <UTC>: revised after <revise url>; changed: <sections>`, and the row stays open; a reply comment is not a revision; while the revise has no amend line after it (`row_revise_pending`) no approval closes the row, an approval older than the amend no longer counts, and a reject still closes), **reject** (`reject: <reason>`, closed as not planned with the label `rejected`). A comment by anyone but the assignee is never an answer, and neither is a comment in no answer form, whoever wrote it: the forms are read on a comment's first line, right-trimmed (`answer_kind` in `lib.sh`, the owner; the board page's `answerKind` and `standingOf` are held to it and to `row_answer_url` by `plugin/tests/board-page.test.mjs`), and a row without a phrase takes only the bare forms. Then the closing session tells each waiting seat one line (the words verbatim and the issue URL) by `SendMessage`, resolved through the roster; a seat that was not reachable finds the row in its inbox (`decision.sh inbox <SEAT>`, computed from acks) at its next wake. The decider answers by typing the approving phrase to the orchestrator or commenting it on the issue. The seat that hears the word closes the issue with the words verbatim and their record (the answer comment, or for words typed to a session the session's own account of them); the board republishes itself. A dated record file is not required: the words live on the row until the wrap-up. An act only the decider can perform carries `hands` and stays open until they report it done.

## Coordination stays private

A public product has a private **twin**: the roster's `repo`, whose `publishes_to` names the public repo. All work and coordination happen in the twin; the public repo receives only publishes, and of the fixed labels only the public set (`templates/labels.json` marks it `"public"`: `bounty` and `awarded`, the bounty and award flow). `init-repo.sh` on a public or public-intended repo (`repo_public_why_at`: the checkout's roster when it has one, then GitHub) creates that set, the bounty template and (with `--token` and `--community`) the award policy only, refuses on stderr every coordination label (the rest of `labels.json`, every `seat:*` and `ws:*`), the decision and workstream templates and the roster, and exits 1 naming any coordination label the repo already carries; it deletes nothing. `bootstrap.sh` refuses a public or public-intended repo outright: a coordinating repo is the private twin. One guard in `lib.sh`, `coord_write_guard <repo> [<seat>]`, runs before the first API write of every coordination write: `decision.sh new`, `record` and `close`; every `desk.sh` write (`open`, and through `desk_of`: `ask`, `answer`, `withdraw`, `msg`, `publish`); `status.sh`; `notes.sh set` and `append`; `ack.sh`; `pr.sh request` and `close`; `board.sh --publish`; `workstream.sh new`; `milestone.sh new`, `move` and `close`; `report.sh milestone --post`. It exits 1 when the target repo is listed (or its owner is) in the roster's `public_intended`, or is public on GitHub (`repo_public_why`, the roster first, then the repo's visibility), naming the rule and the private repo to write in: the seat's roster repo, else the roster's `repo`. There is no override. A pull request on a public repo is not requested or closed through `pr.sh`: `publish.sh` (below) is the only writer to a public repo, and its writes are a publish's own (a push, the PR, its merge, its branch's deletion), never a coordination comment. Readers (`board.sh`, `decision.sh inbox`, `desk.sh inbox`, the relay) still read public repos' existing rows, so history renders.

`join.sh` (through `claude_block_render`) validates the pair with `roster_pair_check`: the roster's `repo` must be private and not public-intended, and `publishes_to`, when present, must be public or public-intended; either failure stops join, naming the field. When the roster has `publishes_to`, the generated CLAUDE.md block opens by naming the repo the private twin of the public one, with the publish steps. The block's protocol pointer is derived (`protocol_repo`): in a checkout of the plugin's own twin, its public repo once that repo, under its own name, carries `docs/protocol.md`, else the twin; in an installed copy without that roster, plugin.json's `repository`.

## Publishing

`publish.sh` (skill `/daita-beast:publish`), run in a checkout of the twin ("twin `main`" below is the twin's default branch on GitHub, "public `main`" the public repo's), is the only writer to the public repo, the roster's `publishes_to`. Its pushes go through one function (`public_push`, the remote `public`, never forced except the one sanctioned force-push, `request --amend`, leased on the PR's head) and its API writes through another (`public_send`, which refuses any path outside `repos/<publishes_to>/`); `coord_write_guard` is unchanged and still refuses every coordination write there. The public repo must exist under its own name before a publish (GitHub serves a renamed or transferred repo's old name as the new one, measured 2026-10-16, so a publish checks the name GitHub answers with); creating it is its owner's act.

1. `publish.sh prepare <slug> [--paths <path>… | --commits <sha>…] [--delete <path>]… --message-file <f>` adds (or checks) the remote `public` and fetches it, then builds ONE new commit in a temporary index on top of the public default branch: `--paths` takes each path as it is in the public view of twin `main` (the overlay, below; a path gone from it is deleted), `--commits` applies each named commit's own change (in topological order, oldest first, never by commit date; each must be on `main` and not a merge) and squashes them. The message is the file, written for outside readers; the author and date are new. The twin's history never travels. When the public repo is empty the branch is an orphan: an empty `Initial commit` root, then the publish commit. The license gate (below, License) and the scrub gate run on the commit before `publish/<slug>` is created: on a miss or a hit nothing is created.
2. **The scrub gate** (`publish.sh scrub <slug> [--body-file <f>]`; also inside `prepare`, `request` and `merge`) first checks the branch's shape: exactly one commit on its public base (the merge base with public `main`), or for an empty public repo the empty root plus one commit, which is what `prepare` makes. Any other branch is refused, naming its commit count: a scan of a longer branch's net diff would pass a phrase one commit adds and the next removes, and `request` would push both commits. A branch with no history in common with public `main` is refused in one line. One owner of the shape: `publish_base` in `publish.sh`. The gate then reads that commit's diff, its message (and the empty root's), and the PR body, and fails, listing every hit as `<file>:<line>`, `<path>: path name`, `commit <sha> message:<line>` or `body:<line>` with its class. The content classes read the added lines of every text file. A binary file (a NUL byte in its first 8000 bytes, the test git uses) is not read, and each one skipped is named on stderr. The classes:
   - **private repo**: an `owner/repo` (or its URL), in any case, of a private repo: every repo the roster names that GitHub reports private, and every private repo of every owner the roster names (`roster_repo_owners`: its `repo`, `publishes_to`, `board` and seat repos), listed in full: an org's through `orgs/<o>/repos?type=private`, trusted only when the gh login is an active member of the org (`user/memberships/orgs/<o>`; GitHub answers a non-member's listing with 200 and an empty list), the gh login's through `user/repos`. A login that is not an active member of an org the roster names, a listing that fails, or another user's account (whose private repos no other login can list), refuses the publish (`scrub_owner_refusal`), naming the owner, the gh login and the rule: **each organization publishes its own public repos from its own twin, with a login that can list that owner's private repos.** A twin whose roster names another organization's or person's repo (its board, say) does not publish that owner's public repos; that owner publishes them from its own twin. `workstream_owners` is not among these owners: joining another owner's workstream adds nothing to what a publish must list. The publish target and exact `public_intended` entries are excepted. A directory that is not a repo (a path inside a private repo) is not listed and goes in the roster's `scrub`.
   - **private name**: the bare name of each of those repos as a whole word, in its exact case (a twin's codename, an ecosystem index's paths). A name shorter than 5 characters is not checked bare, nor is a name in the roster's `scrub_allow`; their `owner/repo` still is.
   - **local path**: `/Users/<name>/` or `/home/<name>/`.
   - **BEAST- line**: a filled-in coordination line, one starting `BEAST-<WORD>` that carries no `<placeholder>` and no `$variable`.
   - **record path**: a `records/` directory under `org/` or `docs/`.
   - **words**: a stretch of 5 consecutive words, at least 2 of them outside a fixed common-word list (English stopwords and the protocol's verbs approve, publish, merge, close, revise, reject, record), of the words on a closed row of the twin (the verbatim words of every close comment on a closed `decision` or `needs-review` row). Words are letters and digits compared case-insensitively; whitespace and punctuation only separate them. A row whose close words are exactly its own approving phrase (its `## Approve with`) is skipped: that phrase is the protocol's, not the decider's prose. The roster's `scrub_allow_words`: a phrase of 5 words or more drops every stretch inside it; a shorter phrase adds its words to the common-word list, so they no longer count toward the 2, and nothing else (a stretch that still carries 2 other uncommon words still hits). One owner of the rule: `WORDS_*` and the allow loop of `scrub_scan` in `lib.sh`.
   - **roster scrub**: a regex of the roster's `scrub` list; a scoped entry only on the text files its globs match.
   - **vendored**: on a file under a directory of the roster's `vendored` (a byte-exact upstream copy), the private repo, private name, words and roster scrub classes are not applied to its content; local path, BEAST- line, record path and path name still are.
   - **path name**: every path the commit adds or changes, binaries included: a secret-shaped file name (`wallet.json`, `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`, `*.p12`, `*.pfx`, `keystore*.json`, `credentials*.json`, case-insensitive), and the private repo, private name and roster scrub classes applied to the path itself.

   One owner: `scrub_patterns` and the scanner `scrub_scan` in `lib.sh` (`publish.sh` runs them on a publish, `license.sh` on a license file's header); the roster's `scrub`, `scrub_allow` and `scrub_allow_words` are parsed by `roster_scrub`, and its `vendored` by `roster_vendored`, in `lib.sh`.

   **The stable contract** for any other tool is `publish.sh scan` and its output, never `lib.sh`, whose functions are internal and change with refactors. `publish.sh scan [--roster <file>] [--patterns-file <f>] (--base <ref> | --tree <dir>) [--paths <path>…]` runs exactly the classes above, through `scrub_patterns` and `scrub_scan`, on the diff `<ref>..HEAD` of the repo you stand in and those commits' messages, or on every file of a directory (`.git` excepted), only under `--paths` when given. It needs no twin checkout. stdout carries one line per hit: `<file>:<line> <class> <match>`, `<path>:0 path-name <match>` for a path, `commit-message <class> <match>` for a message; the classes are `private-repo`, `private-name`, `local-path`, `record-path`, `roster-scrub`, `beast-line`, `words` and `path-name`. It exits 1 on any hit, 0 when clean, and 2 on a usage or pattern error. `publish.sh scan [--roster <file>] --dump-patterns > f` writes the pattern bag (the JSON `scrub_patterns` builds, `"bag": "beast-scrub-patterns/1"`, its `vendored` list required); `--patterns-file f` reads it, so a scan runs with no network.
3. `publish.sh request <slug> --seat <SEAT> --body-file <f>` re-runs the license gate, re-scrubs the branch and the body, pushes the empty root as the public default branch when the repo is empty, pushes `publish/<slug>`, opens the PR on the public repo with the body (an existing open PR from the branch is reused), and files the approval row in the twin (`decision.sh new`, the home repo, `--decides <public>`, the PR's URL in Decision and Record, approved with `publish <slug>`). Beast writes nothing else on the public repo: no label, no assignee, no comment.
4. **Amend** (the decider widened or narrowed a publish after its PR opened). `publish.sh prepare <slug> --amend [--paths … | --commits …] [--delete …] --message-file <f>` rebuilds the slug's ONE commit on the public base as it is now and reruns the license and scrub gates; it is refused when the slug was never requested (no row of its title in the twin), when its row is closed, and when nothing changes. `publish.sh request <slug> --amend --seat <SEAT> [--body-file <f>]` re-gates, then force-pushes `publish/<slug>` with `--force-with-lease` on the open PR's head: the one sanctioned force-push, through `public_push` only. It is refused when the PR branch is not one publish commit on its base (someone else pushed to it). It retitles the PR (and replaces its body when given), then posts ONE line on the twin row: `Amended at <UTC>: <n> files; added <list>; removed <list>; changed <list>` (relative to the replaced commit; each list cut after 8 with a count; `amend_line` and `row_amended_at` in `lib.sh` own the shape). If that line fails to post, rerunning `request --amend` posts it. An approval no newer than the row's latest amend line approved what the amend replaced: `row_answer_url` reads it as not approved and names the amend time, and `merge` on an amended row takes its approval only from the decider's comment on the row (`--record` is refused).
5. The decider answers on the twin's row. `publish.sh merge <slug> --words "<verbatim>" --by <SEAT>` takes the record from the decider's answer comment on the row (`--record` for words typed to a session, recorded first). On the approving forms it refuses when public `main` carries anything twin `main` lacks (run `pull` first), re-scrubs, squash-merges the PR (its title and message the commit's), deletes the public branch, records the new public `main` as merged into twin `main` (a merge commit carrying twin `main`'s own tree, so the next `pull` brings only outside changes; push it), deletes the local branch and closes the row on the words. On `reject: …` it closes the PR unmerged, deletes the branch and closes the row rejected; `revise: …` is not a close.

   **Under a standing latitude.** A seat the decider has given a standing word to merge its own publishes merges with `publish.sh merge <slug> --latitude '<owner/repo> <commit> — <path>' --by <SEAT>` instead of `--words`; the two exclude each other, and `--record` is refused with it. The record is a file at a commit in the seat's own repo (`seat_repo`), which must be private and not public-intended; `latitude_record` in `lib.sh` checks the repo, the commit and the file through GitHub before anything is written. It is refused while a revise is pending on the row (`row_revise_pending`) and on an amended row the decider has not approved since its latest amend line. Everything else is the merge above. The row closes with a close comment that quotes no words; its first line is `Merged under standing latitude <https://github.com/<owner/repo>/blob/<full sha>/<path>> by <seat id>`. That line is never an answer form. The generated board, the board page, the relay's `DECIDED` event (`close=latitude`) and the decider's Cowork digest show it as kind `latitude` with the record linked, so the decider can audit it. Which publishes fall inside a latitude is a rule of the seat's own repo, never of the plugin.
6. `publish.sh release <tag> --title <t> --notes-file <f> [--check]` scrubs the title and the notes and creates a GitHub Release on the public repo at its default branch; `--check` only scrubs. An existing release of that tag with the same title and notes is reused; one that differs dies. `wrapup.sh run` publishes a milestone's release notes through it.
7. `publish.sh pull` merges the public default branch into twin `main` (outside contributions), where `main` is checked out with a clean tree; on a conflict it aborts the merge, names the conflicted files and leaves `main` unchanged. A twin that has never recorded a publish shares no history with its public repo; it is told to record the baseline once (`git merge -s ours --allow-unrelated-histories public/main`) after checking that twin `main` carries everything public has.

**The overlay.** A file `.publish/<p>` on twin `main` publishes as `<p>` at the public root, replacing the twin's own `<p>`: a twin keeps its own instructions and publishes the public version beside them. The twin's root `CLAUDE.md` never publishes; a public `CLAUDE.md` is `.publish/CLAUDE.md`. `--paths .publish/<p>` and `--paths <p>` name the same public path, and a twin path the overlay shadows is never taken from the twin. One owner, `publish_view` in `publish.sh`, decides which twin file publishes at which path. The scrub gate reads the publish commit, so it runs on overlay files at their public paths. `--commits` refuses a commit that touches the root `CLAUDE.md`, `.publish/` or a shadowed path, and names them: publish those with `--paths`.

**Deleting from the public repo.** `prepare --delete <path>` (repeatable; alone or with `--paths` or `--commits`) removes a path from the publish commit's tree while the twin keeps its own copy: a twin-only file, such as the committed `.claude/skills/beast/SKILL.md` coordination pointer, that the public repo must not carry. One source of truth per path: it is refused when the path overlaps a `--paths` item or is shadowed by a `.publish/` overlay file, and when public `main` does not carry it (nothing to delete). The commit message gains a paragraph `Removed from this repository:` listing the paths, and prepare prints them for the PR body.

## License

The roster's `license` names the license every public repo of the roster's owners carries, and its one canonical source:

```json
"license": {
  "name": "Acme Community License, version 1",
  "file": "LICENSE.md",
  "manifest": "SEE LICENSE IN LICENSE.md",
  "source": {"repo": "acme/legal", "path": "licenses/acme-community-v1.tex", "render": "pandoc -f latex -t markdown_strict --wrap=none -L \"$BEAST_SCRIPTS/pandoc/latex-crossrefs.lua\"", "checkout": "/path/to/a/checkout/of/acme/legal"},
  "exempt": ["acme/upstream-math-fork"]
}
```

The roster's top-level `vendored` (Roster, above; never inside `license`, where `roster_license` refuses it naming the top-level field) lists directories that hold byte-exact copies of upstream packages: their `package.json` and plugin manifests are the upstream's, not ours, so the manifest check skips them. Every other tracked `package.json` and `.claude-plugin/plugin.json` in the tree must carry `manifest`; `node_modules` is never read.

`exempt` (optional) lists public repos, `owner/repo`, that are not under the license: a fork of an upstream project that keeps the upstream's own license. `license.sh audit` lists each as `exempt` and reads it no further, so it is never a miss; an entry that names no public repo of the roster's owners is a stale exemption, and the audit exits 1 naming it. An archived repo (read-only on GitHub, so no license can be placed) is listed as "archived", never a miss. `roster_license` dies on an entry that is not `owner/repo` or is listed twice.

`name` is the display name (one line, no `--`); `file` the path the license lives at in each repo; `manifest` the value of `"license"` in `package.json` and every `.claude-plugin/plugin.json`. `source.render` is optional: a shell command that reads the source on stdin and writes the license text; without it the source is copied as it is. It runs with `BEAST_SCRIPTS` set to the plugin's scripts directory, so it can name the filter the plugin ships for a LaTeX source, `pandoc/latex-crossrefs.lua`, and with `LATEX_CROSSREFS_SOURCE` set to the source's file, which the filter reads for the numbering. The filter prints every number as the PDF prints it: the source's `\documentclass` (`article` or `report`) gives the class's `\the<counter>` formats, `secnumdepth` and counter resets, and a `\renewcommand\the<counter>{…}` in its preamble replaces a format (built from `\arabic`, `\Roman`, `\roman`, `\Alph`, `\alph`, `\the<counter>` and plain characters). The document's `\title` becomes the one H1 and every heading moves down a level; each numbered heading carries its number (`III Terms`, `A Definitions`), and a starred heading, or one deeper than `secnumdepth`, carries none; every `\ref` becomes the text LaTeX writes for it (a numbered heading's `\the<level>`, an enumerate item's `\p@enum<n>\theenum<n>` such as `4a`, a starred heading's label the number in force where it sits); the anchors `\label` leaves are dropped. It changes no word of the text. It fails the render on a `\ref` to a label the source does not define, a label on neither a heading nor an enumerate item, a missing source, a command in a format it does not print, or a command that changes the numbering it does not follow (`\setcounter` and its kin on a sectioning or enumerate counter, `\appendix`, `\part`, `\p@<counter>`, an enumerate given enumitem options or `\setlist` around a label), naming it. `source.checkout` is optional: an absolute path to a checkout of `source.repo` on the owner's machine, read at its `HEAD`; without it the source is read through the GitHub contents API. `roster_license` in `lib.sh` is the one parser and dies naming a malformed part.

`license.sh` (skill `/daita-beast:license`) is the one owner of license checks; it reads and never writes to GitHub.

- `license.sh render [-o <file>]` writes the expected file: one neutral header line, `<!-- <name>. Rendered from its canonical source; do not edit by hand. -->`, an empty line, then the render. The header names no repo.
- `license.sh check <dir | tree-ish>` checks a directory or a tree-ish of the repo it runs in, item by item, and exits 1 naming each miss: the file is present; what follows its header (the leading HTML comment) and the empty line equals the render byte for byte; the header is the neutral line and the scrub gate (`scrub_patterns`, `scrub_scan`) finds nothing in any line of it; `package.json` and every `.claude-plugin/plugin.json` say `"license": "<manifest>"`. A directory inside a git work tree is read through its tracked files only (`git ls-files`), so untracked and ignored paths, nested worktrees and `node_modules` are never read; a directory outside one is walked (`.git` and `node_modules` pruned), and stderr says so.
- `license.sh audit` runs the same checks over every public repo of every owner the roster names (`roster_public_owners`: `roster_repo_owners`, the owners of its `repo`, `publishes_to`, `board` and seat repos, plus the owner of every `public_intended` entry; the scrub keeps `roster_repo_owners`, since a public-intended org's private repos are not this twin's to list), at each default branch, through the REST API (a git tree and its blobs; no clone), and prints one table: repo, license file, body matches, header clean, manifests, and the twin seat (the rostered seat whose repo is the private twin that publishes to it, from that repo's roster). It exits 1 when any row misses or cannot be read.

**The license gate.** When the roster has `license`, `publish.sh prepare` and `request` run `license.sh check` on the publish commit and refuse a publish whose public tree misses: prepare creates no branch, request pushes nothing. A twin fixes a miss in itself: `license.sh render -o <file>` and a manifest edit, committed on twin `main`, then `publish.sh prepare <slug> --paths <file> package.json <plugin manifests> --message-file <f>`.

The `license-reviewer` agent runs `audit` and `check` and reports each public repo missing or drifting, with the seat that owns the fix and its publish steps; it never writes, posts or publishes.

## Watching

Seats are told by the machine's relay, a scheduled job (`/daita-beast:relay`, launchd every 120 s): one GitHub search per tick for every roster seat together (`watch.sh --roster --once`), asking only for rows updated since the oldest seat's high-water mark minus an hour (`~/.beast/watch/<login>/<LABEL>.mark`, the start of its last good poll and the query it ran; a seat without one makes the tick a full one: every open row and the closed ones of the last two days), and only when a row of that seat changed (labelled `seat:<login>/<LABEL>`, or with no `seat:` label and filed by it: `row_seats`; a decision, a PR labelled `needs-review`, or the seat's desk: a new ask, answer or message is an UPDATED; a new comment that is only bookkeeping, a `BEAST-ACK`, `BEAST-STATUS`, `BEAST-NOTES` or `BEAST-WATCHDOG` line, a close comment or a publish `Amended at` line, is not), a disposable Haiku session whose only tool is SendMessage sends that seat its event line (`BEAST-EVENT kind=NEW|DECIDED|UPDATED seat=<login>/<LABEL> <title> <url>`, DECIDED carrying `close=<closed|rejected|latitude|none>` after the seat and the close comment's first line) and nothing else; only a seat whose `seats.sh address` says `direct` (same Claude account, same machine, a fresh address) is sent. What a seat sends another seat itself is the seat-to-seat line (Shapes above): `BEAST-MSG from=<identity> to=<identity> re=<ref|none> blocking=no at=<UTC>` then the body, by `SendMessage` on a direct path or as a desk message (`desk.sh msg`) otherwise. Bookkeeping comments (a `BEAST-ACK`, `BEAST-STATUS`, `BEAST-NOTES`, `BEAST-ADDRESS`, `BEAST-COWORK`, `BEAST-WATCHDOG` or `BEAST-WATCHDOG-NOTES` first line, a close comment, a publish amend line: `BOOKKEEPING_FIRST_LINE_RE` in `lib.sh`, one list) are never news, and an edited comment fires nothing. A seat never hears its own act: every seat posts as one login, so the watcher names an event's actors by their tags (`event_actors` in `lib.sh`, over the one tag reader `SEAT_TAG_JQ` that `seat_acks` also reads): a NEW's filer is the seat of the row's first `BEAST-ACK` comment, a DECIDED's closer is the `Closed by seat` of the close comment, and each new comment that is not bookkeeping is written by the seat its tag names (a `BEAST-ACK` first or last line, a `BEAST-ASK` header, a `BEAST-MSG` sender, a `BEAST-WITHDRAW` on the seat's own desk), else by the decider (an untagged comment, a `BEAST-ANSWER`). An event whose every actor is the seat itself is logged `own act, not sent` and not sent; the decider's answer and another seat's act always are, so a desk message from another seat reaches the desk's seat. Reading the actors costs one comments read per NEW, as DECIDED and UPDATED already did; a read that fails leaves the event unfiltered, named on stderr. It runs in the seats' permission mode: a receiver holds a message from a sender in another mode and never tells a one-shot sender, so the relay log says queued, never delivered. No seat holds a monitor; when nothing changed, nothing but the poll runs. A seat whose address is not recorded is not sent and loses nothing: its inbox is computed from the rows' acks. An address the messenger answered "not reachable" for twice running is not sent to again until the seat records a new one (`~/.beast/relay-unreachable.json`; the log says `not sending to <seat> at <address>: not reachable on 2 messenger replies`). A GitHub rate limit (the search quota or the secondary burst limit, `rate_limit_text` in `lib.sh`) is named once, loud (`BEAST-WATCH GitHub rate limit at <UTC>: …; backing off <n> s`), and starts a backoff (`~/.beast/watch/backoff`, 120 s doubling to 1800 s) during which a poll asks GitHub nothing and the log says `poll: skipped`; the next good search clears it. A workstream whose `## Seats` table does not parse is skipped and named once per distinct message (`fault_once`, ledger `~/.beast/watch/faults.json`; `parses again` when it is fixed), and every other workstream is still polled. Any other failure of the watcher is logged `watch failed (exit <n>, named above)`. Nothing is pushed by GitHub itself while every seat shares one login; the day collaborators have their own logins, a co-assignee gets GitHub's own notification.

The machine watchdog is a second scheduled job on the same machine (`install-relay.sh --job watchdog`, launchd every 900 s, Haiku, the seats' permission mode): `watchdog.sh` runs a fixed checklist with no model (quota by the uncharged `rate_limit`; the relay job's program, load state and mode against `$(plugin_root)` and the roster, and its newest `poll:` line; the plugin record against the installed plugin; the live seat sessions, a claim in `~/.beast/sessions.json` with no `ended_at` whose session a live Claude Code session file names (`lib.sh::claude_sessions_read`: session id to name and cwd, the pid alive by `kill -0`; a claim whose session none names is logged `dead-claim: … reported, not re-stamped`, and a session file of another shape is a bug); `~/.beast/relay.log`, `~/.beast/hooks.log` and the live transcripts from their offsets at the last tick; the live seats' addresses; their relay snapshots for rows past a 15-minute ack grace, a row read only when its `updatedAt` moved; on that same read, `row-shape`: an open row waiting on its decider whose required sections are empty or missing by `section_required` over `ROW_SECTIONS` or `PR_ROW_SECTIONS`, `lib.sh::row_shape_missing`). A quiet tick makes no search and starts no session: one `rate_limit` call and one conditional read per tracking issue the live claims name. It repairs on its own what is local and mechanical (re-stamps a live seat's address recorded on this machine whose name is not its claimed session's live name, or that is older than 24 hours, with `seats.sh touch <identity>`: the live name and `at=` now, refused unless the claimed session is live and runs in the seat's home or launch folder, the `## Seats` table re-rendered, no session claimed; records a newer installed plugin with `plugin_root_record` and re-points the relay with `install-relay.sh`, re-measured by `--describe`; deletes a mark the watcher named corrupt; weekly, the relay caches of retired seats and the pre-1.5 watch files), and files bugs on the plugin twin only (labels `bug` and `watchdog`, title `watchdog: <check> <object> — <summary>`, deduplicated by listing the twin's `watchdog` issues, never a search; one new issue a tick, five a day; an open one gets at most one `recurrence` comment a day; a closed one is never reopened). Only a finding that needs `SendMessage` starts the agent `daita-beast:watchdog` (tools `Bash`, `Read`, `SendMessage`, `ListAgents`; `BEAST_WATCHDOG=1`, under which every plugin script but `watchdog.sh` and the hooks refuses to run, `lib.sh::watchdog_guard`): it sends a tagged reminder to the seat's live session name when `ListAgents` lists it, `BEAST-WATCHDOG to=<identity> check=<id> at=<UTC>` then the rows or the fact and the exact command, at most once per seat, check and object every 2 hours, three a tick and one per seat. A `row-shape` reminder goes to the row's filing seat only (`row_filer`, else `row_seats`), once a week per row and set of empty or missing sections, naming the row, the sections and the repair path; the watchdog never edits the row. It never answers, acks, closes, labels, files a row, posts status, records or forgets an address, writes under a home or writes to a public repo; every GitHub write it makes opens `BEAST-WATCHDOG machine=<host>` and is never an answer form. Its memory is `~/.beast/watchdog/state.json` (offsets, ledgers, the row cache) and one comment `BEAST-WATCHDOG-NOTES machine=<host> at=<UTC> entries=<n>` on the Beast workstream's tracking issue, edited in place (`GOTCHA`, `FALSE` and `TUNE` lines, newest first, 60 at most, 30 days at most); three false alarms on a check within a week double its grace or cadence up to a bound. The catalogue it judges by is `plugin/watchdog/gotchas.md`. Every hook appends one line to `~/.beast/hooks.log` on a block or a fault (`hook_log`: `<UTC> <hook> block|fault session=<id> <message>`); the watchdog files each hook and message class once.

## Reading GitHub

One REST quota (5,000 requests an hour) is shared by every seat, the relay and the board of a login, so the plugin reads GitHub conditionally and never re-reads what has not changed. As built in `lib.sh`:

- Every read is `gh_get` (one page) or `gh_get_all` (every page, 100 a page, a full page followed by the next); `row_read <repo> <N>` is the issue and its comments as one JSON, the read the board, the inbox and the desks derive acks, events and words from. Every write is `gh_send`. No other `gh api` call exists in the plugin.
- A read's ETag (or Last-Modified) and body are kept per gh login in `~/.beast/cache/<login>/` (`BEAST_CACHE_DIR` moves the root), written atomically; the next read of the same URL sends `If-None-Match`, and GitHub's 304 serves the cached body without charging the quota (measured 2026-10-15: `gh api -i` prints `HTTP/2.0 304 Not Modified` and the headers with an empty body, exits 1 with `gh: HTTP 304`, and the core `used` count did not move). Every read asks GitHub; the cache never answers alone, so a write is seen by the next read, and an empty cache (a cloud session, Cowork) only costs more.
- A cache entry that does not parse is named on stderr and the read asks GitHub unconditionally and replaces it. A gh failure names the call (`daita-beast: gh <METHOD> <path> failed (exit N…): <gh's words>`), and a body that is not JSON is named as a truncated response and never used or cached.
- What bumps an issue's `updated_at` (measured 2026-10-15): adding a comment and deleting one do; **editing a comment does not**. So no read is skipped on an unchanged `updated_at` (it would serve an edited answer stale), and comments are not read with `since=` (it shows edits but cannot show a deletion; the per-page ETag already charges only the changed pages).
- Search has no ETag (`Cache-Control: no-cache`) and is never cached between runs; it draws on its own quota (30 a minute per login, shared by every seat of that login). The search index lags a write by seconds to minutes (measured: 10 s for one comment; a decision issue created at 23:29:42Z was absent from an `updated:>=` search at 23:35:48Z); the relay's hour of overlap covers it. The issues list lags a create by seconds too (measured: absent at +0 s, listed at +6 s).
- One search per query per run. A run is a top-level script and every script it starts (`join.sh` starts `seats.sh record`, `resume.sh`, `seats.sh list`, `notes.sh`, `decision.sh inbox`, `desk.sh inbox`). The first script of a run makes `$BEAST_WS_CACHE`, a directory, exports it and deletes it at its exit (`on_exit`, which every EXIT cleanup chains through); the scripts it starts inherit it. `search_issues` memoizes one result per query there (`search-<digest of the query>`) and serves every later call of the run from it; `ws_seats_all` memoizes the one seat table (`ws-seats.tsv`), which `ws_seats_write`, the table's one writer, forgets; `workstream_candidates <slug>` reads the run's all-workstreams result when it is there instead of searching again. A re-ask within a run is no fresher than the memo: the index lags a write anyway. A join costs 5 searches. `watch.sh`'s loop form clears the memo before each poll (`run_cache_clear`). A 403 with no quota left prints `<resource> quota: resets at <UTC>, <n> s` from `gh_request`, the one place that sees `X-RateLimit-Remaining` and `X-RateLimit-Reset`.
- `BEAST_CALL_LOG=<file>` appends one line per request: time, status, `charged=yes|no`, quota (`core`, `search`, `write`), path. Measured with it on 2026-10-15: `board.sh --assignee <login>` costs 307 core cold and 0 core warm (318 requests answered 304; only its 3 searches are charged), byte-identical output; `decision.sh inbox` for five seats costs 15–145 core cold and 0 warm.

## Seat homes

A seat's home is the directory the seat works in once seated: its root. Seating sets it; where the session started does not. In VS Code every session starts in the folder the window opened it in (the launch folder) and its shell returns there after every command; Claude Code loads that folder's CLAUDE.md and keys auto-memory off it. So any number of seats share a launch folder or a VS Code window, and two seats never share a home. `seat.sh new <LABEL> --repo-path <checkout> --agent <name> --workstream <slug>` (skill `/daita-beast:seat`), run from the repo's main checkout, refuses a public or public-intended repo, then in one act adds the roster row, creates the home, adds the seat to the workstream issue's `## Seats` table (`workstream.sh seat-add`, which renders the master's CLAUDE.md block and every home block of the workstream on this machine) and opens the seat's desk (`desk.sh open`, which reuses an existing one). The row stores only the portable part, `home: {kind, branch}`. The local path is derived from the kind by one function, `seat_home_path` in `lib.sh`:

| Kind | Path | Branch | Chosen when (unless `--kind` is given) |
|---|---|---|---|
| checkout | the repo's main checkout | whatever is checked out (`null`) | no other seat of this login is homed in the checkout |
| worktree | `<repo-parent>/<repo>.seats/<LABEL>` | `seat/<LABEL>` (re-used when it exists) | the checkout is taken and the repo has no submodules or nested git repos |
| wrapper | `~/.beast/homes/<login>/<LABEL>` | `null` | the checkout is taken and the repo has submodules or nested git repos (a worktree would not carry them) |
| subdir | `<checkout>/<dir>` (roster `dir`, no `branch`) | whatever is checked out | never picked: `--kind subdir --dir <dir>`, a directory of the checkout that is not a repo root, is not inside another repo, has its own CLAUDE.md and homes no other seat; a dir without one is refused naming the stub line, and `--stub` writes it: an import of the nearest CLAUDE.md above it by relative path (`@../CLAUDE.md`), or a heading when there is none (`seat.sh::subdir_stub`) |

A repo's main checkout, where its roster, its seats' homes and its publish branches are read, is the checkout whose git dir is its common dir (`checkout_is_main`): a plain checkout, or a twin checked out as a git submodule (its `.git` a file, its git dir the superproject's `.git/modules/<path>`); a linked worktree's git dir is `<common>/worktrees/<name>`, so it is not. `checkout_root` (`git rev-parse --show-toplevel`) is the one test of "is this inside a checkout", `checkout_require_root` of "is this a checkout's root", and `repo_main_root` resolves a linked worktree or a wrapper to the main checkout through the common dir's `core.worktree` (a submodule's modules dir records it) or the directory holding `.git`; no script tests `-d .git`.

Every home carries `.beast/seat.json` (`{"id", "kind"}`, and for a wrapper `"root"`, the checkout it wraps); everything else about the seat is read from the roster. It is machine-local: checkout and worktree homes ignore it in their `.gitignore`, a subdir home as `<dir>/.beast/seat.json` in the checkout's. A wrapper holds a `CLAUDE.md` that is `@<checkout>/CLAUDE.md`, a blank line and the Beast block, and an executable `claude.sh` that runs `claude --add-dir <checkout>` from the wrapper. The launcher is an optional way into a wrapper for terminal users: `--add-dir` loads the repo's agents, skills and the imported CLAUDE.md, while `permissions.additionalDirectories` in settings loads none of them and the import is denied (measured 2026-10-15, twice, with a negative control). `seat.sh new` refuses a home path that exists and is not this seat's, a checkout that already homes another seat, and a `seat/<LABEL>` branch checked out elsewhere (it names the path, and says when that tree has uncommitted changes). `seat.sh where <seat>`, from any directory, prints the home and kind on this machine (found as join finds it); `seat.sh retire <seat>` removes the seat from its workstream's `## Seats` table (`workstream.sh seat-remove`, which re-renders the master block and the Beast block of every home of the workstream on this machine), sets `"retired": "<date>"` on the row and removes nothing else.

The plugin's SessionStart hook (`seat-hello.sh`) reads `$PWD/.beast/seat.json` for the seat's id and the roster for everything else (its tracking issue through the workstream's labels). In a home (the seat's derived home is `$PWD` and its row is not retired) it adds context naming the seat's identity, its role, its first act (`join.sh`), its recorded address with its age, and its handoff duty; after a compaction (source `compact`) it leads with "post the handoff now"; when other seats are listable from that folder too (a home that is also a workspace's launch folder), it names the home's seat as the folder's, gives its first act for a session that is that seat, and lists the others. Anywhere else (a retired seat's home included: it is named as retired, never offered) it lists the gh login's seats a session there can take, each with its `join.sh <LABEL>`: those of every VS Code workspace file (found walking up from `$PWD` to `$HOME`) that lists `$PWD` in any position, else every seat of the login rostered on this machine, a retired one excepted; it claims none, the person or the session names the seat; with none it prints nothing. Every context line opens with `scripts: <plugin>/scripts` (`lib.sh::plugin_root`: `$CLAUDE_PLUGIN_ROOT`, else the root `~/.beast/plugin.json` records), or with the install hint when there is neither; the committed block names no machine path. A fault (a malformed seat.json or workspace file, gh without a login) is put into the context, named. Before any of this the hook decides whether to rejoin (Rejoining, below). There is no PreCompact reminder: Claude Code discards a PreCompact hook's `systemMessage` and `continue` fields, and its only control is blocking the compaction.

## Joining a seat

A seat joins, and rejoins after every reload or compaction, with one command from any directory: `join.sh <SEAT>` (skill `/daita-beast:join`). Seating sets the root. Join finds the seat on this machine (`seat_locate` in `lib.sh`, the one owner, also behind `seat.sh where`) through the checkouts it can name: the launch folder's own checkout, the folders of every VS Code workspace file (walking up from the launch folder to `$HOME`) that lists the launch folder in any position, and the machine index `~/.beast/checkouts.json` (`{"<main checkout>": {recorded_at}}`, machine-local, written by `seat.sh new`, `bootstrap.sh` and every join). The seat's row is the one in the roster of the checkout of its own repo (a peer row, `"home": null`, is not); a row is read only from a roster that passes the 1.5.0 check (`roster_check_unique`, so every row carries a workstream and an identity is built from it), and a checkout whose roster fails it is named once on stderr, `<path>: roster fails the 1.5.0 check: <why>; not searched`, and skipped (`seat_homes_on_machine`); a bare label naming several seats, or one seat rostered in two checkouts, is refused naming the candidates. It refuses when no roster it can name has the seat (`no seat <LABEL> in any roster this machine can name (searched: <rosters>); to create it: /daita-beast:seat <LABEL>`), when a roster names the seat for a repo with no checkout here (naming the clone and `seat.sh new` steps), and when the home's `.beast/seat.json` names another seat. Its first line is `SEATED <id> at <home>`. Every step then runs against the home: it finds the seat's workstream tracking issue by the labels of the row's `workstream` (a new seat is created by `seat.sh new`, never by join), prints `role: <agent> at <path>` (the agent file, checked to exist; a terminal session runs it with `claude --agent <name>` from the home), records the session's address, regenerates the Beast block in the home's CLAUDE.md (the repo's for a checkout or worktree home, the wrapper's own for a wrapper, the subdir's own for a subdir) from `plugin/templates/claude-block.md` for this seat: its identity, its role, and its workstream's `## Seats` table rendered from the tracking issue (the only Beast text a seat's repo carries, never hand-edited), triages the auto-memory folder this session loads (below), runs the resume (handoff, notes, inbox), and ends naming the home's CLAUDE.md to read now. From then on the session's root is the home: every shell command starts with `cd <home> &&` or uses `git -C <home>` and absolute paths, every file edit uses an absolute path under the home, and the home's CLAUDE.md is reread after any compaction. A roster row without a `home` is read as a checkout home, and join says once to record it with `seat.sh new <SEAT> --kind checkout`. A role change is `join.sh <SEAT> --agent <name>`, a move to another workstream `join.sh <SEAT> --workstream <slug>` (then the seat maps of both workstreams, by `workstream.sh seat-remove|seat-add` and `render`); a retirement is `seat.sh retire`.

Join also records the session claim: `session: <id> holds <identity>` (`lib.sh::sessions_claim`: this session's `$CLAUDE_CODE_SESSION_ID`, the time, the launch folder and the tracking issue, in the seat's `~/.beast/sessions.json` entry; a claim another session held moves to `previous`). `seats.sh record` records it too. Outside a Claude Code session there is no id and join says nothing is recorded. The SessionEnd hook (`seat-bye.sh`) marks the claims of an ending session `ended_at`.

**Rejoining.** The SessionStart hook (`seat-hello.sh`, input `session_id` and `source`) rejoins a seated session by itself:
- **Held.** The session's id is a seat's current claim, as after a compaction or a resume, which keep the id. The hook rejoins.
- **Restart.** On `startup` or `clear` the id is new. The hook rejoins the one seat whose current claim was made from this launch folder by a session that has ended (`ended_at`). A claim whose session recorded no end may belong to a session that is still open: an idle open session writes nothing, and there is no other liveness to read without the network. So the hook does not rejoin it. It gives the exact `join.sh` line, says why, and says when that session's transcript was last written. Several ended claims from this folder get their join lines and no rejoin.
- **Taken.** The session's id is among a seat's `previous` claims: another session on this machine claimed the seat since. The hook does not rejoin. It names that session, when it claimed the seat and where it was launched, and lists the seats this session can take.
- **Claimed elsewhere.** Before any rejoin the hook reads the seat's `BEAST-ADDRESS` comment on the tracking issue the claim recorded (one gh call, `lib.sh::seat_addresses_at`). An address recorded after the claim (`session_at`, or the cached `recorded_at`) was recorded by another session, on this machine or another. The hook does not rejoin and names that address, its machine, account and time. Machine clocks are compared as they are.
- **Gone.** A seat no longer rostered on this machine, or retired, is never rejoined. Nor is one whose tracking issue or address cannot be read: the hook names the fault and gives the join line.

To rejoin, the hook runs `join.sh <identity>` for the session, and its context carries the join output: `SEATED`, the address recorded, the handoff, the notes, the inbox, and the home's CLAUDE.md to read. Join records the session's address itself: `seats.sh record` with no address reads the session's live name from its Claude Code session file (`claude_session_of`, by the hook's `session_id`), through the same code path as a record by hand, claiming nothing join has not. When that file cannot be read, the context leads with the one line `address: not recorded — <the failure>` and the manual record line. After a compaction it leads with "post the handoff now". A session with no claim, and no claim made from its launch folder on a restart, reads nothing and gets the context it would get without one.

## Seat memory

Four kinds, four owners. The ROLE (obligations, tools, invariants) is the agent file the roster row names (`agent`: the plugin's generic `daita-beast:seat`, whose body points at the home's Beast block as the owner of the obligations, or the repo's own agent that specializes it with its domain and one line `Seat role: daita-beast:seat`) and the repo's CLAUDE.md, served by the repo and shared by every seat of that role; a session never carries it. The SEAT's working state (what it does, waits on, leaves behind) is its `BEAST-STATUS` comments on its tracking issue: a `handoff` before a compaction, reload or surface switch, `resume.sh <SEAT>` after (the newest handoff, the notes, decisions decided meanwhile, open ones waiting). The seat's durable facts, the things it must not relearn on another surface, are its one `BEAST-NOTES` comment (`notes.sh <SEAT> show|set|append`). Auto-memory is keyed by the launch folder, so every seat started in one folder shares it: it holds only short pointers and lessons true for all of them, a cache on one machine that is never the only copy of anything another surface needs. Join reports the memory folder this session loads (`lib.sh::session_memory_dir`: the project folder holding the session's transcript, `$CLAUDE_CODE_SESSION_ID.jsonl`, else the launch folder encoded as Claude Code does, every character but A-Z, a-z, 0-9 and `-` replaced by `-`), never a home's, and triages each file and each `MEMORY.md` index line (`lib.sh::memory_triage`): a lesson (frontmatter `type` feedback, user or reference) is never flagged; one that names another seat is that seat's (`owned by <id>; leave it`), never in the joining seat's list; a short pointer (a tracking-issue ref within `MEMORY_POINTER_MAX` bytes) is kept, for any seat, so per-seat one-line pointers in a shared `MEMORY.md` are allowed; only seat STATE (a handoff, a recorded address, branch or worktree state, inbox items, a next act) is listed to delete or cut to a pointer. The `seat-clerk` agent drafts a seat's inbox digest, acks, handoff and memory triage, and posts nothing.


A specialist the seat hires (an agent in the home repo's `.claude/agents`) keeps its own memory by declaring `memory: project`: `.claude/agent-memory/<name>/` in the repo, committed, loaded into that specialist only. Seat working state never goes there; specialist memory holds what the specialist learns about its craft in this repo.
## Workstreams

A workstream has a slug, its id. Opened with `/daita-beast:workstream` (`workstream.sh new --slug <slug> …`): one Project (private by default), one tracking issue labelled `workstream` and `ws:<slug>` in the master repo (the issue's repo; `workstream_master <slug>`), its `## Seats` table empty, and at least one milestone (`--milestone "<title>|<YYYY-MM-DD>|<what it delivers>"`, created on the coordinating repo before anything else is written; the tracking issue's `## Milestones` section links the repo's milestones page). Work items are the issues and PRs the work produces, added to the Project. Acceptance is stated at opening and measured at closing; the final `done` status carries the evidence. Residue (branches, worktrees, fixtures) is the seat's defect, cleaned before `done`.

**Workstreams under another owner.** Discovery searches the workstream owners, one owner function (`workstream_user_terms` in `lib.sh`): the owners the roster names (`repo`, `board`, `seats[].repo`) plus the roster's declared `workstream_owners`. `workstream_issue`, `workstream_candidates`, `ws_seats_all`, `seat_repo`, a bare label's resolution and `resume.sh`'s handoff search all read it; an owner neither named nor declared is never searched. So a seat in `acme/app-dev` whose roster declares `"workstream_owners": ["threejs"]` joins workstream `scenes` whose tracking issue is `threejs/three-dev#1`: `seat.sh new … --workstream scenes` and `workstream.sh seat-add` write that issue's `## Seats` table, and `join.sh` records the seat's address there. Without the declaration the lookup dies naming `workstream_owners`. The master stays private and not public-intended: every write to it (`ws_seats_write`, the master's CLAUDE.md block, the address, status and notes) passes `coord_write_guard`, which refuses a public master under any owner. The seat's roster row still names its own repo (no peer rows); the foreign master lists the seat only in its `## Seats` table.

The seat map is the tracking issue's `## Seats` table, the one owner of which seats are in the workstream with their repo, home and agent: `workstream.sh seat-add <slug> <login/LABEL> --repo <owner/repo> --home "<kind [arg]>" --agent <name>` (the repo private and not public-intended, the agent file existing; `seat.sh new` runs it), `seat-remove <slug> <login/LABEL>` (both end with the render below), `seats <slug>` (prints it). `workstream.sh render <slug> [--pr]` writes the master repo's CLAUDE.md block for the workstream (`plugin/templates/workstream-block.md`, between `<!-- beast:workstream begin <slug> -->` and `<!-- beast:workstream end <slug> -->`; a master of several workstreams carries several blocks; a hand edit is undone by the next render): into the local checkout of the master when this machine has one (then it prints the commit command), else through the contents API on the default branch with the sha read first (a file that changed meanwhile is a 409, exit 1, nothing written), or with `--pr` on the branch `beast/workstream-<slug>` with a pull request opened once; then it re-renders the Beast block of every home on this machine of a seat in the table (`lib.sh::ws_homes_render`; a home without a block yet is named and left to its join). `ws_seats_all` (every open workstream's table across the workstream owners) is the one enumeration of all seats: `seats.sh list` and a bare label's resolution read it; no roster indexes other repos' seats.

## Milestones and dependencies

A seat sets out its own milestones and moves them itself, so it schedules its work rather than waiting to be asked. A milestone is a GitHub milestone on the repo its items live in; a seat's are on its home. The shape has one owner, the `milestone_*` functions in `lib.sh`:

- **Title**: one line, no `"` (the ask header quotes it) and no `|` (`workstream.sh --milestone` splits on it).
- **Due date**: GitHub's `due_on`, the only copy. It is written at 12:00 UTC: measured 2026-10-16, a `due_on` of `T00:00:00Z` is stored as the day before, `T12:00:00Z` keeps the date; every write reads the stored date back and dies when it differs.
- **Description**: fixed lines, written only by `milestone_desc`: `Delivers: <one line>`; `Moved: later|earlier — <why>` (the latest move only, no history); one `Waits on: <ref>` per dependency; `Report: <one line>` (the latest participant report's summary).

`milestone.sh` (skill `/daita-beast:milestone`): `new <title> --due <date> --delivers <text> [--waits-on <ref>]...` (an identical rerun reuses the milestone; one that differs dies naming it), `list`, `move <title> --due <date> --why <line>` (a move carries its why), `close <title> [--carry <next>]`. `close` refuses while open issues or PRs are filed under the milestone, or open desk asks name it in their header, naming each; `--carry` files them under the next open milestone (an ask's header is edited in place and its desk republished) and closes.

**Every row, ask and PR names one.** `decision.sh new` (and so `record`), `desk.sh ask`, `pr.sh request` and `publish.sh request` take `--milestone "<title>"` and refuse an item without one while the repo it is filed in has any open milestone, listing them (`milestone_require`); the milestone is GitHub's own field on the issue or PR, and on a desk ask the header's `milestone="<title>"`. `publish.sh request` files its approval row in the twin under the twin's milestone and checks it before anything is pushed; nothing is set on the public PR.

**Dependencies as data.** `--waits-on <seat | owner/repo#N>` (repeatable) on `decision.sh new`, `desk.sh ask` and `milestone.sh new` writes one line per dependency, `Waits on: <ref>` (`waits_on_line`; `WAITS_ON_RE` is the one shape, read by `waits_on_parse` and `desk_parse`; a `Waits on:` line that is not the shape fails loud). `deps.sh <SEAT>` (skill `/daita-beast:deps`) reads the declarations on the seat's open decision rows in its home, its open desk asks and its home's open milestones (`deps_declared`), and measures each (`dep_state`):

| State | A row (`owner/repo#N`) | A seat |
|---|---|---|
| released | closed completed, not rejected; a PR merged | no open milestone in its home and a closed one (the latest) |
| delayed | open, and its milestone is overdue or was moved later (the why) | its soonest open milestone is overdue or was moved later |
| changed direction | closed not planned or labelled `rejected`; a PR closed unmerged; open with the decider's newest answer `revise:` | — |
| waiting, on time | open and not late | its soonest open milestone is not late |
| waiting, no milestone | — | its home has never set a milestone |

A changed direction carries the row's link, and the first line of the words only when the reader's home is the row's own repo: the words stay in the home where they were said.

**Due flags.** `decision.sh inbox` opens with the seat's home milestones due within 3 days or overdue, one line each (nothing when none is); `board.sh` adds a section `## Milestones due within 3 days or overdue` for the roster's home repos, naming the seats homed in each; the Cowork page flags them on the desk chips (`docs/board-ui.md`), reading them off the rows it fetches, since the GitHub connector has no tool that lists milestones.

## Participant report

At a milestone's close, `report.sh milestone <title> [--repo <owner/repo>] --post --by <SEAT>` (skill `/daita-beast:report`) sends ONE report addressed per participant, so nobody searches the traffic to learn that what they wait on has released, slipped or changed direction. Participants are every seat of the roster plus every outside contributor (a login holding no seat) awarded on the milestone's items. A section says:

- what the participant earned this milestone: the `BEAST-AWARD` comments on the issues and PRs filed under it, read through `ledger.sh` for every month the milestone spans, in the token of the checkout's `.beast/award-policy.md` (a repo without one awards nothing, and the section says so). An award goes to a login; it counts for a seat of that login when the item carries the seat's label, and is named in the summary as unattributed otherwise. A ledger run that drops a comment stops the report: a report with holes is never sent;
- the state of each thing it waits on (`deps_declared` and `dep_state`, the measure `deps.sh` prints).

Where it is kept: each seat's section is a `BEAST-MSG` on its desk (`desk.sh msg`, from `--by`), and the milestone's description keeps the summary as its one `Report:` line (the latest only). Records and dated files are deleted at wrap-up, so no report file is written. Every seat must have a desk; the script checks before its first write and refuses naming the seats without one. An outside contributor has no desk: their section is printed for the seat to deliver (public release notes come with wrap-up). Without `--post` the script prints every section and writes nothing.

## Wrap-up

A decision recorded against a past release can be active drift against the current one, and a board with hundreds of spent comments hides the open ones. At a milestone's end, `wrapup.sh` (skill `/daita-beast:wrapup`) folds what the milestone decided into the docs, publishes release notes, and deletes the milestone's coordination traffic. Run it in a checkout of the repo the milestone is on (default: the roster `repo`). Deleting an issue needs admin rights and cannot be undone. So the plan is approved on a row first, and the run deletes nothing the approved plan does not list.

1. `wrapup.sh plan <M> [--carry <next>]` reads GitHub and writes `.beast/wrapup/<slug>/plan.json` in the checkout, posting nothing. Its cutoff is the plan's own time. It lists three things:
   - **delete:**
     - the closed `decision` rows filed under `M`;
     - the coordination comments of the closed `needs-review` PRs under `M` (`BEAST-` lines and close comments; GitHub cannot delete a PR);
     - on the repo's desks, every ask answered or withdrawn, with its answer, when it is under `M` or under no milestone and answered before the cutoff, and every message older than the cutoff;
     - on the tracking issues of the seats homed in the repo, the `BEAST-STATUS` and `BEAST-ACK` comments older than the cutoff, except each seat's newest handoff;
     - the files under a records directory (`RECORD_PATH_RE`) that a closed row names in its `## Record` or close comment and that exist on the default branch;
     - the plan's own directory.
   - **keep:**
     - the open items under `M` (issues, PRs, open asks naming it), carried to `--carry`, by default the soonest other open milestone; the plan dies when there are open items and nowhere to carry them;
     - closed issues that are not board rows;
     - each seat's newest handoff;
     - every `BEAST-NOTES` and `BEAST-WATCHDOG-NOTES` comment, listed.
   - **fold in:** each closed row's url, title, state, words and record, and the milestone's `Report:` line.

   One owner of the shape: `plan_build` and `plan_check` in `wrapup.sh` (`beast-wrapup-plan/1`).
2. `wrapup.sh request <M> --seat <SEAT>` commits the plan file to the default branch through the contents API (that one path), removes the local copy, and files one row, `Decision: Wrap up <M>`, approved with `wrap up <M>`. The row's Decision carries `Plan: <blob url at that commit>` and `Plan digest: sha256:<hex>`. It is filed under the plan's carry milestone (else `M`), so the next wrap-up deletes it.
3. **The fold-in** (the realign skill, scope b): `wrapup.sh brief <M>` prints the rows. The seat writes each into the as-built docs and instruction surfaces, deleting what it supersedes, and commits the doc changes in ONE commit whose message cites the url of every row it folded. A row with nothing to fold is listed in the same commit as `dropped: <url> — <why>` in `.beast/wrapup/<slug>/fold-in.md`. A red-team or investigation record survives only if the fold-in writes its useful content into the docs.
4. `wrapup.sh run <M> --words "<verbatim>" --by <SEAT> --fold-in <sha> [--notes <f>] [--tag <tag>]` checks everything before writing anything. It refuses:
   - when the words do not approve;
   - when the decider's standing answer on the row is not the approve (`row_answer_url`, the reader `publish.sh merge` shares);
   - when the plan at the linked commit does not carry the digest;
   - when the fold-in commit is not on the default branch;
   - when a closed row of the plan is neither cited by its url in the fold-in commit's message nor dropped in its manifest (each such row is named);
   - when rows are cited but the commit changes no file outside the plan's directory;
   - when the release notes fail the scrub gate.

   Then it writes, in order:
   1. the release notes, by default the merged PRs' titles, the approved decisions' titles and `report.sh milestone <M> --outside-notes` (the outside contributors, without private links), as a GitHub Release on `publishes_to` through `publish.sh release` (tag: the milestone's slug), or printed when the roster has no `publishes_to`;
   2. the deletes, each through `wrapup_delete`, the one delete of the plugin, which asserts the target repo is the plan's, re-reads the target and logs one line to stdout and `.git/beast/wrapup-<slug>.log`. Issues go by GraphQL `deleteIssue` (closed ones only, the node id the plan names), comments by REST, and the files (records and the plan's directory) by one commit on the default branch through the git data API. An item already gone is logged and skipped, so a rerun completes an interrupted run;
   3. the desks of the plan republished;
   4. `milestone.sh close <M> [--carry <next>]`, before the row's close, so an interrupted run is rerun on the still-open row (its re-check after a carry re-reads for up to 60 s: the issues list lags a milestone change);
   5. one comment on the `--by` seat's tracking issue, `milestone <M> closed: <release link>, <n> rows folded[, <d> dropped]`, posted once (a rerun finds it);
   6. the row closed on the words, which republishes the board;
   7. the DeSciX KB manifests (`.descix/manifests/*.json`) whose sources cover a file the fold-in or the deletes changed, each with `descix kb corpus sync -a <app> -k <kb>` (dry run first) at the plugin's CLI pin (`DESCIX_CLI_PKG` and `descix_cmd` in `lib.sh`, the one owner of the version every printed `descix` command runs) for the seat to run after pulling and pushing.

## Realign

The realign skill (`/daita-beast:realign`, scripts in `plugin/scripts/realign/`) is the procedure the fold-in follows, and the same procedure for a person's own agentic system. It anchors to what is built, folds each live rule into its instruction surface or doc, deletes what has drifted (never annotates it), never touches protected paths, and leaves a report as the next window's seed. It has two scopes:

- **(a) personal system:** every `CLAUDE.md`, the agents and skills, `docs/`, memory, the dated records and the KB corpora, after any significant milestone. A record whose rule is live becomes one line on its instruction surface; a spent one is deleted.
- **(b) workstream:** the wrap-up's fold-in above, ending in the fold-in commit and its manifest.

## Award ledger

**Token authority.** A repo's award policy, `.beast/award-policy.md` (`init-repo.sh <repo> --path <checkout> --token <SYMBOL> --community <owner/repo>`), carries two lines: `Token: <SYMBOL>` and `Community: <owner/repo>`, the repo that holds the token's community. The community repo commits `.beast/awarders.json`, the one owner of which repos may award its token:
```json
{"token": "ACME", "awarders": ["acme/widgets", "threejs/three"]}
```
Exactly the keys `token` (the symbol) and `awarders` (a non-empty list of `owner/repo`, each once, compared case-insensitively). `award.sh` and `bounty.sh` parse the policy (`award_policy`), then read the file from the community repo's default branch through GitHub (`community_awarders`) and refuse a repo it does not list (`award_authority_check`), naming the community repo, the file and the missing entry, before anything is written. A community repo without the file refuses every award of its token, naming the file to create and its shape; there is no open default. A malformed file, or one for another token, dies naming the community repo and the file. A policy without a `Community:` line dies naming the line.

`ledger.sh --community <TOKEN> --repos <a,b> --month <YYYY-MM> --out <dir>` (skill `/daita-beast:ledger`) computes a month's awards from GitHub, never a second ledger: every `BEAST-AWARD` comment on an issue or PR labelled `awarded` in the repos. A row is kept when the comment parses, its token is `--community`, it was made in the month, and its author's role on that repo, read live (`repo_permission`), is admin or maintain. Every other comment is named on stderr as `DROPPED <url>: <reason>` and the run exits 2. A role that cannot be read (a 403: the gh login lacks push access to the repo) stops the run with exit 1, naming the repo, the login and GitHub's answer, before any file is written: an award is never dropped for an unread role. It writes `<out>/<month>.jsonl` (one row per award: repo, item, to, token, amount, for, ref, by, at) and `<out>/<month>.md` (totals per login and the award list); the community owner commits them to the community repo. A row's `ref` is the award's own `ref=`, or, when the comment carries none, the awarded item's URL (the issue or pull request the comment sits on), so no row has an empty `ref` (the platform's Offers import refuses an empty one, `REF_REQUIRED`). A `ref=` that is present but empty or not an https URL (`AWARD_REF_RE`, lib.sh, the one owner of the shape; `award.sh --ref` refuses any other) stops the run with exit 1, naming the item, the author and the value, before any file is written.

**The offers sheet.** `ledger.sh … --sheet <out.csv> --emails <map.csv> [--batch <name>]` also writes the same rows (the reader of the `.jsonl`, not a second one) as the CSV the DeSciX platform's Offers import reads, the one bridge from GitHub awards to airdrop offers: the import reads only a sheet, never the `.jsonl`. Header `contactemail,token,new_amount,batch,wallet_address`, then one row per award: `contactemail` the recipient's email from the map, `token` the award's token, `new_amount` its amount as written in the award (a plain decimal: no thousands separator, no symbol), `batch` `awards-<YYYY-MM>` unless `--batch` (letters, digits, `.`, `_`, `-`, at most 64), `wallet_address` always blank: the wallet binds when the offer is accepted in Powch. No other column is emitted (never `offer_id`, `offered_at`, `sent_at` or `current_holdings`); fields follow RFC 4180 quoting, lines end in LF. The import matches columns by header name, case-insensitively, and refuses a row with neither wallet nor email (`ROW_NO_WALLET_NO_EMAIL`), so no row is emitted without an email. The login→email map is the platform's data, a file the caller owns: a CSV whose first line is the header `login,email` and every other non-empty line `<login>,<email>`, no quoting, logins compared case-insensitively. A map that lacks that header, has a line that is not one login and one email, lists a login twice, or maps no login at all dies naming the file and the line, before anything is read from GitHub. An awarded login the map lacks refuses the whole run, naming every unmapped login, before any file (sheet, `.jsonl` or `.md`) is written, and exits 1. The sheet carries email addresses, so `--sheet` must be outside every git checkout: a path inside one, ignored or not, is refused before anything is read. A run that drops a comment still writes the sheet without it and exits 2. The path from award to token: ledger → sheet → the platform's Offers import → the recipient accepts the offer in Powch, binding their wallet → the airdrop settles.

A ledger bound for a public repo is published in the token's community repo: when `--out` is in a checkout whose origin is public or public-intended, every repo in `--repos` must be listed in that repo's `.beast/awarders.json` for `--community` (`award_authority_check`), else the run is refused before anything is read. A ledger bound for a public repo lists only public repos. When `--out` is in a checkout whose origin is public or public-intended (`repo_public_why_at`), every repo in `--repos` must be too; a private one is refused, naming it, before anything is read, because its item URLs, award reasons and logins would publish. An `--out` in no checkout is scratch: `report.sh` reads the ledger there for a private milestone's participant report, and fails when the ledger exits with anything but 0 or 2.

Activity per login (merged PRs, reviews given, issues closed) and per seat (decisions executed, status reports) for a period is `report.sh` (the `reporter` agent renders it), computed from GitHub the same way.
