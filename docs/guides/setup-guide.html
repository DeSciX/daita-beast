Setting up Beast

Who needs Beast and how to install it, on each surface Claude runs on. The worked example is DeSciX/egpt-godsworld: first one outside developer who installs nothing, then the maintainer who runs Beast in the project's private twin, then a hypothetical organization, the Three.js maintainers, adopting Beast. As built in daita-beast 1.6.3, checked against the scripts on 2026-10-21. At 19:59 UTC that day the marketplace DeSciX/DAITA pinned daita-beast ref "1.6.3" (since its commit cd0fb37, 19:41 UTC), and tag 1.6.3 of DeSciX/daita-beast was commit 944397c, whose plugin/.claude-plugin/plugin.json reads 1.6.3; so a marketplace install was 1.6.3 at that time.

In short
  • A contributor needs no Beast. Finding a bounty, sending a pull request and receiving an award all happen on the public GitHub repo; receiving the tokens happens in DeSciX and Powch. See section 1 and Token rewards.
  • Beast is a set of conventions on GitHub issues, labels and comments, plus a Claude Code plugin (daita-beast) whose scripts write them. GitHub holds every state. There is no Beast server.
  • All coordination happens in a private repo. This covers decisions, desks, tracking issues, status and acks. A public repo such as DeSciX/egpt-godsworld receives only publishes, bounties and awards. The scripts refuse a coordination write to a public repo, and nothing overrides that. So a public project has a private twin, and the twin is where its maintainer installs Beast.
  • The setup order on a machine: tools, plugin, permissions, plugin record, bootstrap.sh, a workstream, a seat, join, the relay, a test decision, the watchdog, the decider's connector. Each step has a check that must pass before the next one.
  • Organizations meet through declared owners. A seat joins a workstream mastered under another GitHub owner when its roster lists that owner in "workstream_owners", and each organization publishes its own public repos from its own twin. Seats under a second GitHub login are not yet supported; that and the other limits are under Gaps with evidence.
  • Whose GitHub identity, quota and Claude account each call uses is covered in Beast messaging paths. This guide does not repeat it.

1. A contributor: one bounty, nothing to install

Invented for the example: carol-dev, an outside developer.

Carol finds an issue labelled bounty on DeSciX/egpt-godsworld, forks the repo and opens a pull request with Closes #<n> in its description. A maintainer merges it in GitHub and posts the award as a comment that mentions her, so GitHub notifies her. She installs no plugin, takes no seat and needs no DeSciX account for any of that.

To receive the tokens she needs two things outside GitHub: a DeSciX account whose verified email is the one the community owner has for her GitHub login, and a wallet in Powch to accept the offer the platform emails her. The whole path, with what each step checks, is in Token rewards, section 2.

2. The words this guide uses

TermWhat it is on GitHub or on disk
SeatA role held by one GitHub login under a LABEL (upper case) in one workstream. Its identity is <slug>/<LABEL>/<login>. A Claude Code session "takes" a seat with join.
Roster.beast/roster.json, committed in a private repo. It lists that repo's own seats, the people (exactly one owner, who is the decider), and optionally publishes_to (the public twin).
WorkstreamA GitHub Project plus one tracking issue labelled workstream and ws:<slug>. The issue's ## Seats table is the one list of seats in the workstream.
Master repoThe repo the tracking issue lives in. It must be private.
TwinA private repo whose roster names a public repo in publishes_to. Work happens in the twin, and publish.sh is the only thing that writes to the public repo.
DeciderThe roster's owner. Decisions and PR reviews are assigned to this person, who answers in a comment such as approve, revise: … or reject: ….
HomeThe directory a seat works in: the checkout, a worktree, a wrapper or a subdirectory. Two seats never share a home.
Relay, watchdogTwo optional per-machine scheduled jobs. The relay polls GitHub and messages a seat's session when a row of that seat changes; the watchdog checks the relay, the seats' addresses and unacked rows every 15 minutes.

4. The maintainer: Beast in the egpt-godsworld twin

Real: DeSciX/egpt-godsworld (public) and its private twin, owned by a personal account that is also its only decider; the twin's roster names DeSciX/egpt-godsworld in publishes_to (read 2026-10-21). The twin is written <owner>/<twin> below, its owner <owner>, its checkout ~/code/egpt-godsworld-twin. Invented for the example: the seat label LEAD, the workstream scenes and its milestone.

Run the steps in order, and confirm each check before moving on. ${CLAUDE_PLUGIN_ROOT} is the installed plugin's directory, which Claude Code sets for you.

  1. Tools. 
    command -v gh jq git python3
gh auth status
gh auth refresh -s project      # only if you will open workstreams (GitHub Projects)
    Check: four paths print, and the status says Logged in.
  2. Install the plugin (in Claude Code): 
    /plugin marketplace add DeSciX/DAITA
/plugin install daita-beast@daita
/plugin install daita@daita     # the DeSciX connector; set it up with /daita:descix-setup
    Check, after the next session start: claude plugin list shows daita-beast@daita enabled, and the session's start context carries the scripts: <plugin dir>/scripts line once the repo is bootstrapped (step 5). The version on DeSciX/daita-beast main is gh api repos/DeSciX/daita-beast/contents/plugin/.claude-plugin/plugin.json -q .content | base64 -d | jq -r .version; a marketplace install gets the version the marketplace pins (1.6.3 on 2026-10-21 at 19:59 UTC).
  3. Permissions (once per repo). This adds the 15 gh and git read rules a seat needs to <checkout>/.claude/settings.json. Run it without --write first to see the diff. 
    ${CLAUDE_PLUGIN_ROOT}/scripts/permissions.sh ~/code/egpt-godsworld-twin
${CLAUDE_PLUGIN_ROOT}/scripts/permissions.sh ~/code/egpt-godsworld-twin --write
git -C ~/code/egpt-godsworld-twin add .claude/settings.json && git -C ~/code/egpt-godsworld-twin commit -m "Beast permissions"
    Check: a second run prints nothing to add: … already allows the 15 Beast rules.
  4. Plugin record (once per machine, and again after every plugin update, followed by steps 9 and 11): 
    source ${CLAUDE_PLUGIN_ROOT}/scripts/lib.sh && plugin_root_record "${CLAUDE_PLUGIN_ROOT}"
jq -r .version ~/.beast/plugin.json      # must equal the installed version
  5. Bootstrap the twin. This writes the labels, the issue templates (decision, workstream, bounty), the roster skeleton, and the committed cloud pointer .claude/skills/beast/SKILL.md. It refuses a repo that is public or public-intended, naming the twin rule. Its next-step lines print the DeSciX CLI at the plugin's one pin, DESCIX_CLI_PKG in plugin/scripts/lib.sh, as npx -y -p <that package> descix …. A LANE: <name> line in the repo's root CLAUDE.md is optional: without one, seat rows are written with no lane key, and seat.sh new prints lane: none (…). 
    ${CLAUDE_PLUGIN_ROOT}/scripts/bootstrap.sh --repo <owner>/<twin> --path ~/code/egpt-godsworld-twin --seat LEAD
    Then edit .beast/roster.json. It needs exactly one people[] row whose role contains owner (bootstrap writes you as owner), plus "publishes_to": "DeSciX/egpt-godsworld". Commit .beast/, .github/ISSUE_TEMPLATE/ and .claude/skills/beast/. Check: cd ~/code/egpt-godsworld-twin && ${CLAUDE_PLUGIN_ROOT}/scripts/seats.sh list runs without a prompt.
    For bounties and awards on the public repo, write its award policy into the same checkout, naming the public repo: 
    ${CLAUDE_PLUGIN_ROOT}/scripts/init-repo.sh DeSciX/egpt-godsworld --path ~/code/egpt-godsworld-twin --token EGPT --community DeSciX/EGPT
    --token and --community go together; one without the other is refused: daita-beast: --token and --community go together: the award policy names the token and the community repo that holds its .beast/awarders.json. On the public repo it runs in its public mode (only the bounty and awarded labels; see Token rewards, section 3). bootstrap.sh also takes --token and --community, but its policy names the repo it bootstraps, the private twin, which takes no outside contributions.
  6. Open the workstream. Write the goal in the owner's own words to a file, then: 
    printf '%s\n' "Community scenes for Maxi in egpt-godsworld." > ~/code/egpt-godsworld-twin/northstar.md
cd ~/code/egpt-godsworld-twin && ${CLAUDE_PLUGIN_ROOT}/scripts/workstream.sh new --slug scenes --owner <owner> \
  --title "WS: Maxi scenes" --repo <owner>/<twin> \
  --northstar-file northstar.md \
  --milestone "M1 First community scenes|2026-11-30|Scenes from outside contributors merged and awarded"
    Check: the tracking issue carries workstream and ws:scenes, and cd ~/code/egpt-godsworld-twin && ${CLAUDE_PLUGIN_ROOT}/scripts/workstream.sh seats scenes prints an empty table.
  7. Create the seat. Prefer /daita-beast:seat LEAD: it talks the scope through with you first, then runs: 
    ${CLAUDE_PLUGIN_ROOT}/scripts/seat.sh new LEAD --repo-path ~/code/egpt-godsworld-twin --agent daita-beast:seat --workstream scenes
    That one command writes the roster row (held by your gh login), creates the home, adds the row to the ## Seats table, renders the master's CLAUDE.md block and opens the seat's desk. It refuses a public repo as a seat's repo. Check: seat.sh where LEAD prints the home, and the table shows the row. Commit the roster.
  8. Join, in every session, from any directory: /daita-beast:join LEAD. It runs join.sh LEAD, which records this session's address (its name, read from Claude Code's session file). Check: the first line is SEATED scenes/LEAD/<your login> at <home>. From then on every shell command starts with cd <home> &&. Join records that this session holds the seat, and the SessionStart hook rejoins it by itself after a compaction or a resume, and after a restart in the same launch folder once the SessionEnd hook has recorded the earlier session's end; it does not rejoin a seat another session has claimed since (docs/protocol.md:282-289, "Rejoining").
  9. Relay (optional; one per machine). The relay's messenger must run in the permission mode your seat sessions run in. Record it in the roster as "relay": {"permissionMode": "<mode>"}, then: 
    ${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --repo ~/code/egpt-godsworld-twin --permission-mode default
${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --status
${CLAUDE_PLUGIN_ROOT}/scripts/relay.sh --repo ~/code/egpt-godsworld-twin --dry-run     # one poll, sends nothing
    You lose nothing without it. Every seat gets the same inbox from decision.sh inbox LEAD.
  10. Test decision (needs the relay from step 9). From the seat's home, file a test decision assigned to yourself: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/decision.sh new --repo <owner>/<twin> --assignee <your login> \
  --by LEAD --title "FIXTURE install $(date -u +%Y-%m-%dT%H:%MZ)" --milestone "M1 First community scenes" \
  --decision "Close this fixture." --unblocks "the install check" --waits "nothing" --recommendation "approve" \
  --approve-with "approve" --record "$(git rev-parse --short HEAD) — .beast/roster.json"
    --by names the filing seat: the row is labelled seat:<login>/LEAD beside every --seat, the label is read back after the write, and the seat's seen ack is the row's first comment. --milestone is required while the repo has an open milestone (step 6 made one). Your own filing is never sent back to you: within two relay ticks (about 4 minutes) ~/.beast/relay.log says own act, not sent: NEW <url>. Then answer as the decider, with an untagged comment on the row (gh issue comment <url> --body approve). Check: a BEAST-EVENT kind=UPDATED line arrives in the session. Close it: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/decision.sh close <url> --words approve --record <the comment url> --by LEAD
    and the log says own act, not sent: DECIDED <url>.
  11. Watchdog (optional; one per machine, beside the relay, in the same permission mode): 
    ${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --job watchdog --repo ~/code/egpt-godsworld-twin --permission-mode default
${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --job watchdog --status
    It runs every 900 seconds. Check: the installed net.descix.daita-beast.watchdog … line names watchdog.sh in the plugin, and within one tick ~/.beast/watchdog.log carries a tick: line. A fixture row left unacked for 15 minutes after the decider's answer brings a reminder whose first line opens BEAST-WATCHDOG to=<your identity> check=unacked.
  12. The decider's connector. If the decider answers from Claude.ai, give them docs/connector-access.md and publish their board page with /daita-beast:board-ui. Check: they fetch one known private issue by number through the connector.

VS Code with several repos in one window: every session starts in the launch folder, and join finds the seat's home in any folder of that workspace. Run steps 3 and 5 once per repo, and steps 2, 4, 9 and 11 once per machine.

Publishing to DeSciX/egpt-godsworld, and pulling contributions back

The twin's owner publishes from the twin's main checkout, as their seat. The rule: each organization publishes its own public repos from its own twin, with a login that can list that owner's private repos. The twin's owner is a personal account, so only that login can publish it.

cd ~/code/egpt-godsworld-twin
${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh prepare award-policy --paths .beast/award-policy.md .github/ISSUE_TEMPLATE/bounty.md --message-file msg.txt
${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh request award-policy --seat LEAD --body-file body.md --milestone "M1 First community scenes"
# the decider answers on the twin's approval row:  publish award-policy
${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh merge award-policy --words "publish award-policy" --by LEAD
git -C ~/code/egpt-godsworld-twin push

prepare builds exactly one new commit on the public main branch; the twin's history never travels. A scrub gate runs inside prepare, request and merge. It refuses private repo names, local paths, BEAST- lines, words from the twin's closed decisions, roster patterns and secret-shaped file names. If it finds anything it lists every hit and creates nothing.

Outside contributions merged on the public repo come back with publish.sh pull, run in the twin's main checkout with a clean tree. publish.sh merge refuses while the public main has commits the twin lacks, so pull first. If the pull conflicts it aborts, leaves main unchanged and names the files. A pull that merges ends with pulled public … into twin main (…); push it: git push origin main.

5. Cloud: Claude Code on the web

Plugins are not installed in a cloud session. Instead, the repo carries the committed pointer .claude/skills/beast/SKILL.md, which step 5 above writes. The session clones the plugin and runs its scripts over REST:

git clone --depth 1 https://github.com/DeSciX/daita-beast "$HOME/daita-beast"
$HOME/daita-beast/plugin/scripts/decision.sh inbox LEAD
$HOME/daita-beast/plugin/scripts/resume.sh LEAD

Limits that come from the surface, not from Beast:

  • GraphQL is blocked, so the workstream and Project verbs refuse there. Open workstreams from a machine.
  • Only the repos attached to the session can be reached.
  • No relay runs, so the inbox at each wake is how the seat hears anything.
  • The proxy appends _Generated by Claude Code_ to the issues it creates.

6. Cowork or Claude.ai chat

  1. Customize › Plugins › Add marketplace DeSciX/DAITA › install daita-beast (and daita).
  2. Run /daita-beast:connector. Its step 0 fetches one known private issue by number to prove access. If it is denied, install the GitHub app on that account or organization; docs/connector-access.md has the details.
  3. /daita-beast:board-ui publishes the decider's board page: the open decision issues and the open pull requests labelled needs-review assigned to the decider, across every organization the connector reaches.
  4. Create a scheduled task, every 15 minutes or more, whose prompt is exactly /daita-beast:cowork-tick <owner>/<twin>.

Roster rows and seat homes are shell acts, so create them from a machine.

7. A hypothetical organization: the Three.js maintainers adopt Beast

Hypothetical: the scenario is invented for this guide, and it implies no endorsement by, or involvement of, the Three.js project, its maintainers or the mrdoob and threejs accounts. Real: mrdoob/three.js (public, owned by the user account mrdoob), the organization account threejs, DeSciX/egpt-godsworld (public) and its private twin <owner>/<twin> from section 4. Invented: the private repo threejs/three.js-dev, the maintainer logins alice-three and bob-three, and the workstream studio, which does not exist on GitHub.

(a) The Three.js workstream master must be a private twin

The maintainers cannot make mrdoob/three.js the master. Every coordination write first passes one guard, coord_write_guard, which refuses any repo that is public on GitHub or listed in the roster's public_intended. Nothing overrides it. Its two refusals read:

The roster's repo is the public repo (exit 1): 
daita-beast: refused: mrdoob/three.js is public on GitHub, and the roster …/.beast/roster.json names it as the repo of this roster. Coordination stays private: a seat's home is a private repo (the twin; its roster names the public repo in "publishes_to"). Move the roster row to the twin; no coordination write goes to mrdoob/three.js.
The roster's repo is the private twin, and the write aims at the public repo (exit 1): 
daita-beast: refused: mrdoob/three.js is public on GitHub. Coordination stays private: decision rows, desks, tracking issues, status, notes, acks, review requests and the board are written only in a private repo; a public repo receives only publishes. Write it in threejs/three.js-dev.
These are the texts of plugin/scripts/lib.sh:2629 and :2631 with the example's names; they were measured read-only against a throwaway roster on 2026-10-20, with a private repo passing with exit 0 as the control, and the guard is unchanged in 1.6.3.

Other checks enforce the same rule. bootstrap.sh refuses a public repo as the coordinating repo. init-repo.sh gives a public repo only the public labels (bounty, awarded). seat.sh new refuses a public repo as a seat's repo. Rendering a seat's CLAUDE.md block, which join does, refuses a roster whose repo is public or whose publishes_to is private.

The setup the maintainers can use:

  1. An owner of the threejs organization creates the private repo threejs/three.js-dev (gh repo create threejs/three.js-dev --private). Creating a repo is the owner's act; Beast never creates one.
  2. Run section 4 steps 1–8 in a checkout of it, with "publishes_to": "mrdoob/three.js" in the roster and exactly one owner in people[].
  3. Not yet supported (deferred): seats alice-three/THREE and bob-three/THREE, each maintainer running seat.sh new THREE … under their own gh login. The scripts key a seat by login and label, so two people can each hold a THREE seat, but no run with a second login exists (Gap 1).
  4. Release to mrdoob/three.js with publish.sh. Only mrdoob can run it, as an active member of the threejs organization: this roster names threejs (its repo) and mrdoob (publishes_to, a personal account whose private repos only mrdoob can list). Any other login is refused, naming the owner and the login. GitHub answers a non-member's private repo listing with HTTP 200 and an empty list (measured 2026-10-20 with a login outside threejs: gh api 'orgs/threejs/repos?type=private' → 200, 0 repos), so the scrub reads the login's membership (user/memberships/orgs/threejs) first and refuses a login that is not an active member.

(b) The Three.js maintainers join a workstream in the egpt-godsworld twin

Suppose the egpt-godsworld twin's owner opens a workstream studio for Three.js scene work. It is hypothetical: no such workstream exists. Its master is the twin <owner>/<twin>. The Three.js seats stay in their own twin, threejs/three.js-dev, and join studio because their roster declares <owner> in "workstream_owners". Workstream discovery searches the owners a roster names (repo, board, seat repos) plus its workstream_owners; an owner not declared is never searched. The master stays private: every write to it passes coord_write_guard.

Deferred, not yet supported: steps 2 to 5 act under the Three.js maintainers' own logins, in a repo another login owns. No run with a second login exists (Gap 1); these steps are described from the scripts.

  1. Open the workstream in the egpt-godsworld twin, as <owner>, whose seat LEAD from section 4 publishes. On a personal account only that user can create the workstream's Project: 
    cd ~/code/egpt-godsworld-twin && ${CLAUDE_PLUGIN_ROOT}/scripts/workstream.sh new --slug studio --owner <owner> \
  --title "WS: Three.js scenes for Maxi" --repo <owner>/<twin> \
  --northstar-file northstar.md \
  --milestone "M1 Three.js scenes|2026-12-15|Three.js scenes Maxi can load"
  2. Grant access (GitHub, not Beast; the owner's act). A joining seat writes the master's ## Seats table and CLAUDE.md block and records its address on the tracking issue, so each Three.js login needs write access to the twin: 
    gh api -X PUT repos/<owner>/<twin>/collaborators/alice-three
gh api -X PUT repos/<owner>/<twin>/collaborators/bob-three
    Each call sends an invitation; the access starts only when the invitee accepts it. On a personal-account repo an accepted collaborator gets write access.
  3. Declare the owner in the Three.js roster. In threejs/three.js-dev's .beast/roster.json add, at the top level, "workstream_owners": ["<owner>"], and commit it. The field is a list of GitHub owner names, each once, none of them an owner the roster already names; anything else stops every lookup, naming the field. Without it, seat.sh new … --workstream studio dies with no open issue labelled workstream and ws:studio among user:threejs: … a tracking issue under another owner is searched only when this roster's "workstream_owners" lists that owner.
  4. Each maintainer creates a seat in studio, from the Three.js checkout, logged in as themselves: 
    cd ~/code/three.js-dev && ${CLAUDE_PLUGIN_ROOT}/scripts/seat.sh new STUDIO --repo-path ~/code/three.js-dev --agent daita-beast:seat --workstream studio
    The roster row stays in threejs/three.js-dev (a roster refuses peer rows); the seat appears in studio's ## Seats table on the twin's tracking issue. The identity is studio/STUDIO/alice-three. Commit and push the roster, then /daita-beast:join studio/STUDIO/alice-three.
  5. Get a PR reviewed in the twin. The seat works on a branch of the twin and opens a PR on <owner>/<twin> with the hand-back body (## What, ## Evidence, ## Review against the engineering rules, ## Closes), then: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/pr.sh request <owner>/<twin>#42 --seat alice-three/STUDIO --unblocks "the M1 scenes" --recommendation "merge: the scenes load in Maxi, evidence in the PR" --assignee <owner> --milestone "M1 Three.js scenes"
    This writes the two texts into the PR body as ## Unblocks and ## Recommendation (both required; without either the request is refused before anything is written), labels the PR needs-review and seat:alice-three/STUDIO (read back after the write), assigns <owner> and posts the requesting seat's seen ack. The PR then appears as a row of the decider's board. The decider answers on the PR with a comment whose first line is the PR's approving phrase (the first quoted phrase of a ## Approve with section, else approve), <phrase> — <comment>, a bare approve or approved, revise: <what> or reject: <why>. On approval the seat runs pr.sh close <owner>/<twin>#42 --merge --words "approve" --record <the answer comment url> --by alice-three/STUDIO.
  6. Publish to DeSciX/egpt-godsworld as <owner> from the twin's main checkout, as in section 4. workstream_owners adds no owner to what a publish lists, so the Three.js seats change nothing there.

(c) Public developers

Outside developers never touch a twin. They fork and open an ordinary pull request on DeSciX/egpt-godsworld or mrdoob/three.js, as Carol does in section 1. Beast puts no review machinery on public PRs: pr.sh refuses a public repo. A maintainer with write access on the public repo reviews and merges in GitHub, and the twin then runs publish.sh pull. Bounties and awards are allowed on public repos, and the public repo serves as the bulletin board. See Token rewards.

Gaps: what 1.6.3 does not do for these examples

  1. Seats under a second GitHub login are not yet supported. The protocol says "Every seat posts as the decider's login today" (docs/protocol.md:126; plugin/scripts/pr.sh:11-13), and docs/design/adopting.md:88 says seats under a second GitHub login "are designed (the roster's github field differs, and GitHub would send its own notifications) but have not been run with a second login". Steps (a)3 and (b)2 to 5 are deferred until one is run.
  2. Beast has no command for granting access. Adding collaborators, creating the twin and creating the public repo are GitHub acts by the owner (plugin/skills/publish/SKILL.md:8: "creating it is its owner's act").
  3. DeSciX/egpt-godsworld carries no award policy or bounty template yet. Measured 2026-10-21 at 19:37 UTC: .beast and .github returned 404, and the repo had no bounty issue. A maintainer writes them with init-repo.sh (step 5) and publishes them (section 4).
