Setting up Beast

How to install Beast and set it up for a project, on each surface Claude runs on, with a worked example: the Three.js maintainers adopt Beast to work on egpt-frqtl STUDIO and egpt-godsworld scenes. As built in daita-beast 1.5.10, checked against the scripts on 2026-10-20. At 20:12 UTC that day the marketplace DeSciX/DAITA pinned daita-beast ref "1.5.9", tag 1.5.9 of DeSciX/daita-beast, so a marketplace install is 1.5.9 until the pin moves.

In short
  • Beast is a set of conventions on GitHub issues, labels and comments, plus a Claude Code plugin (daita-beast) whose scripts write them. GitHub holds every state. There is no Beast server.
  • All coordination happens in a private repo. This covers decisions, desks, tracking issues, status and acks. A public repo receives only publishes. The scripts refuse a coordination write to a public repo, and nothing overrides that. A public project such as mrdoob/three.js therefore needs a private twin, and the twin is the workstream master.
  • The setup order on a machine: tools, plugin, permissions, plugin record, bootstrap.sh, a workstream, a seat, join, the relay, a test decision. Each step has a check that must pass before the next one.
  • Organizations meet through declared owners. A seat joins a workstream mastered under another GitHub owner when its roster lists that owner in "workstream_owners", and each organization publishes its own public repos from its own twin. Seats under a second GitHub login are not yet supported; that and the other limits are under Gaps with evidence.
  • Whose GitHub identity, quota and Claude account each call uses is covered in Beast messaging paths. This guide does not repeat it.

1. The words this guide uses

TermWhat it is on GitHub or on disk
SeatA role held by one GitHub login under a LABEL (upper case) in one workstream. Its identity is <slug>/<LABEL>/<login>, for example studio/THREE/alice-three. A Claude Code session "takes" a seat with join.
Roster.beast/roster.json, committed in a private repo. It lists that repo's own seats, the people (exactly one owner, who is the decider), and optionally publishes_to (the public twin).
WorkstreamA GitHub Project plus one tracking issue labelled workstream and ws:<slug>. The issue's ## Seats table is the one list of seats in the workstream.
Master repoThe repo the tracking issue lives in. It must be private.
TwinA private repo whose roster names a public repo in publishes_to. Work happens in the twin, and publish.sh is the only thing that writes to the public repo.
DeciderThe roster's owner. Decisions and PR reviews are assigned to this person, who answers in a comment such as approve, revise: … or reject: ….
HomeThe directory a seat works in: the checkout, a worktree, a wrapper or a subdirectory. Two seats never share a home.
RelayAn optional per-machine scheduled job. It polls GitHub and messages a seat's session when a decision for that seat changes.

3. Local: Claude Code on your machine

Run the steps in order, and confirm each check before moving on. ${CLAUDE_PLUGIN_ROOT} is the installed plugin's directory, which Claude Code sets for you.

  1. Tools. 
    command -v gh jq git python3
gh auth status
gh auth refresh -s project      # only if you will open workstreams (GitHub Projects)
    Check: four paths print, and the status says Logged in.
  2. Install the plugin (in Claude Code): 
    /plugin marketplace add DeSciX/DAITA
/plugin install daita-beast@daita
/plugin install daita@daita     # the DeSciX connector; set it up with /daita:descix-setup
    Check, after the next session start: claude plugin list shows daita-beast@daita at the version the marketplace pins (1.5.9 on 2026-10-20). The version on DeSciX/daita-beast main is gh api repos/DeSciX/daita-beast/contents/plugin/.claude-plugin/plugin.json -q .content | base64 -d | jq -r .version.
  3. Permissions (once per repo). This adds the 15 gh and git read rules a seat needs to <checkout>/.claude/settings.json. Run it without --write first to see the diff. 
    ${CLAUDE_PLUGIN_ROOT}/scripts/permissions.sh ~/code/three.js-dev
${CLAUDE_PLUGIN_ROOT}/scripts/permissions.sh ~/code/three.js-dev --write
git -C ~/code/three.js-dev add .claude/settings.json && git -C ~/code/three.js-dev commit -m "Beast permissions"
    Check: a second run prints nothing to add: … already allows the 15 Beast rules.
  4. Plugin record (once per machine, and again after every plugin update): 
    source ${CLAUDE_PLUGIN_ROOT}/scripts/lib.sh && plugin_root_record "${CLAUDE_PLUGIN_ROOT}"
jq -r .version ~/.beast/plugin.json      # must equal the installed version
  5. Bootstrap the repo. This writes the labels, the issue templates (decision, workstream, bounty), the roster skeleton, and the committed cloud pointer .claude/skills/beast/SKILL.md. It refuses a repo that is public or public-intended, naming the twin rule. Its next-step lines print the DeSciX CLI at the plugin's one pin, npx -y -p @descix/cli@4.2.0 descix …. A LANE: <name> line in the repo's root CLAUDE.md is optional: without one, seat rows are written with no lane key, and seat.sh new prints lane: none (…) (as does bootstrap.sh when given --orchestrator). Pass --token <SYMBOL> --community <owner/repo> only if the repo takes outside contributions for rewards; bootstrap.sh passes both to init-repo.sh, which writes the award policy and is the one place that checks they come together. One without the other is refused: daita-beast: --token and --community go together: the award policy names the token and the community repo that holds its .beast/awarders.json. See Token rewards. 
    ${CLAUDE_PLUGIN_ROOT}/scripts/bootstrap.sh --repo threejs/three.js-dev --path ~/code/three.js-dev --seat THREE --board threejs/three.js-dev
    Then edit .beast/roster.json. It needs exactly one people[] row whose role contains owner (bootstrap writes you as owner), plus "publishes_to": "mrdoob/three.js" if there is a public twin. Commit .beast/, .github/ISSUE_TEMPLATE/ and .claude/skills/beast/. Check: cd ~/code/three.js-dev && ${CLAUDE_PLUGIN_ROOT}/scripts/seats.sh list runs without a prompt.
  6. Open the workstream. Write the goal in the owner's own words to a file, then: 
    printf '%s\n' "Three.js capabilities in egpt-frqtl STUDIO, and community scenes for Maxi in egpt-godsworld." > ~/code/three.js-dev/northstar.md
cd ~/code/three.js-dev && ${CLAUDE_PLUGIN_ROOT}/scripts/workstream.sh new --slug studio-scenes --owner threejs \
  --title "WS: STUDIO capabilities and Maxi scenes" --repo threejs/three.js-dev \
  --northstar-file northstar.md \
  --milestone "M1 STUDIO capabilities|2026-11-30|Three.js features usable from egpt-frqtl STUDIO" \
  --repos "threejs/three.js-dev — coordination, mrdoob/three.js — the library"
    Check: the tracking issue carries workstream and ws:studio-scenes, and cd ~/code/three.js-dev && ${CLAUDE_PLUGIN_ROOT}/scripts/workstream.sh seats studio-scenes prints an empty table.
  7. Create the seat. Prefer /daita-beast:seat THREE: it talks the scope through with you first, then runs: 
    ${CLAUDE_PLUGIN_ROOT}/scripts/seat.sh new THREE --repo-path ~/code/three.js-dev --agent daita-beast:seat --workstream studio-scenes
    That one command writes the roster row (held by your gh login), creates the home, adds the row to the ## Seats table, renders the master's CLAUDE.md block and opens the seat's desk. Check: seat.sh where THREE prints the home, and the table shows the row. Commit the roster.
  8. Join, in every session, from any directory: /daita-beast:join THREE. It runs join.sh THREE --address "<this session's ListAgents name [ref]>", filling the address in for you. Check: the first line is SEATED studio-scenes/THREE/<your login> at <home>. From then on every shell command starts with cd <home> &&. Join records that this session holds the seat (session: <id> holds <identity>), and the SessionStart hook rejoins it by itself after a compaction or a resume, and after a restart in the same launch folder once the SessionEnd hook has recorded the earlier session's end; it does not rejoin a seat another session has claimed since (docs/protocol.md:267, "Rejoining").
  9. Relay (optional; one per machine). Pick the permission mode your seat sessions run in, then: 
    ${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --repo ~/code/three.js-dev --permission-mode default
${CLAUDE_PLUGIN_ROOT}/scripts/install-relay.sh --status
${CLAUDE_PLUGIN_ROOT}/scripts/relay.sh --repo ~/code/three.js-dev --dry-run     # one poll, sends nothing
    You lose nothing without it. Every seat gets the same inbox from decision.sh inbox THREE.
  10. Test decision (needs the relay from step 9). From the seat's home, file a test decision assigned to yourself: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/decision.sh new --repo threejs/three.js-dev --assignee <your login> \
  --by THREE --seat THREE --title "FIXTURE install $(date -u +%Y-%m-%dT%H:%MZ)" --milestone "M1 STUDIO capabilities" \
  --decision "Close this fixture." --unblocks "the install check" --waits "nothing" --recommendation "approve" \
  --approve-with "approve" --record "$(git rev-parse --short HEAD) — .beast/roster.json"
    --by names the filing seat; its seen ack is the row's first comment. --milestone is required while the repo has an open milestone (step 6 made one). Your own filing is never sent back to you: within two relay ticks (about 4 minutes) ~/.beast/relay.log says own act, not sent: NEW <url>. Then answer as the decider, with an untagged comment on the row (gh issue comment <url> --body approve). Check: a BEAST-EVENT kind=UPDATED line arrives in the session. Close it: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/decision.sh close <url> --words approve --record <the comment url> --by THREE
    and the log says own act, not sent: DECIDED <url>.

VS Code with several repos in one window: every session starts in the launch folder, and join finds the seat's home in any folder of that workspace. Run steps 3 and 5 once per repo, and steps 2, 4 and 9 once per machine.

4. Cloud: Claude Code on the web

Plugins are not installed in a cloud session. Instead, the repo carries the committed pointer .claude/skills/beast/SKILL.md, which step 5 above writes. The session clones the plugin and runs its scripts over REST:

git clone --depth 1 https://github.com/DeSciX/daita-beast "$HOME/daita-beast"
$HOME/daita-beast/plugin/scripts/decision.sh inbox THREE
$HOME/daita-beast/plugin/scripts/resume.sh THREE

Limits that come from the surface, not from Beast:

  • GraphQL is blocked, so the workstream and Project verbs refuse there. Open workstreams from a machine.
  • Only the repos attached to the session can be reached.
  • No relay runs, so the inbox at each wake is how the seat hears anything.
  • The proxy appends _Generated by Claude Code_ to the issues it creates.

5. Cowork or Claude.ai chat

  1. Customize › Plugins › Add marketplace DeSciX/DAITA › install daita-beast (and daita).
  2. Run /daita-beast:connector. Its step 0 fetches one known private issue by number to prove access. If it is denied, install the GitHub app on that account or organization; docs/connector-access.md has the details.
  3. /daita-beast:board-ui publishes the decider's board page.
  4. Create a scheduled task, every 15 minutes or more, whose prompt is exactly /daita-beast:cowork-tick threejs/three.js-dev.

Roster rows and seat homes are shell acts, so create them from a machine.

6. Worked example: Three.js adopts Beast

Hypothetical: the scenario is invented for this guide, and it implies no endorsement by, or involvement of, the Three.js project, its maintainers or the mrdoob and threejs accounts. Real: mrdoob/three.js (public, owned by the user account mrdoob), DeSciX/egpt-frqtl and DeSciX/egpt-godsworld (public), the private twin of DeSciX/egpt-frqtl, owned by a personal account that is also its decider (written <owner>/<twin> below, its owner <owner>). Invented for the example: the private repo threejs/three.js-dev and the maintainer logins alice-three and bob-three.

(a) The Three.js workstream master must be a private twin

The maintainers cannot make mrdoob/three.js the master. Every coordination write first passes one guard, coord_write_guard, which refuses any repo that is public on GitHub or listed in the roster's public_intended. Nothing overrides it. The guard, run read-only on 2026-10-20 against a throwaway roster:

Roster repo set to the public repo, then coord_write_guard mrdoob/three.js (exit 1): 
daita-beast: refused: mrdoob/three.js is public on GitHub, and the roster …/.beast/roster.json names it as the repo of this roster. Coordination stays private: a seat's home is a private repo (the twin; its roster names the public repo in "publishes_to"). Move the roster row to the twin; no coordination write goes to mrdoob/three.js.
Roster repo set to the private twin, with a write aimed at the public repo (exit 1): 
daita-beast: refused: mrdoob/three.js is public on GitHub. Coordination stays private: decision rows, desks, tracking issues, status, notes, acks, review requests and the board are written only in a private repo; a public repo receives only publishes. Write it in threejs/three.js-dev.
Control: the same guard on a private repo (the private twin of DeSciX/egpt-frqtl) passed with exit 0.

Other checks enforce the same rule. bootstrap.sh refuses a public repo as the coordinating repo. init-repo.sh gives a public repo only the public labels (bounty, awarded). seat.sh new refuses a public repo as a seat's repo. join refuses a roster whose repo is public, or whose publishes_to is private.

The setup the maintainers can use:

  1. An owner of the threejs organization creates the private repo threejs/three.js-dev (gh repo create threejs/three.js-dev --private). Creating a repo is the owner's act; Beast never creates one.
  2. Run section 3 steps 1–8 in a checkout of it, with "publishes_to": "mrdoob/three.js" in the roster and exactly one owner in people[].
  3. Not yet supported (deferred): seats alice-three/THREE and bob-three/THREE, each maintainer running seat.sh new THREE … under their own gh login. The scripts key a seat by login and label, so two people can each hold a THREE seat, but no run with a second login exists (Gap 1).
  4. Release to mrdoob/three.js with publish.sh (below). Only mrdoob can run it, as a member of the threejs organization. The rule: each organization publishes its own public repos from its own twin, with a login that can list that owner's private repos. This roster names threejs (its repo) and mrdoob (publishes_to, a personal account whose private repos only mrdoob can list), so any other login is refused with that rule, naming the owner and the login. A login that is not an active member of threejs is refused as well: GitHub answers a non-member's private repo listing with HTTP 200 and an empty list (measured 2026-10-20 with a login outside threejs: gh api 'orgs/threejs/repos?type=private' → 200, 0 repos), so the scrub reads the login's membership (user/memberships/orgs/threejs) first. The refusal reads daita-beast: refused: the roster … names the owner threejs (its repo, publishes_to, board or a seat repo), and the gh login <login> cannot list threejs's private repos (<login> is not an active member of the organization threejs (…), and GitHub answers a non-member's private repo listing with an empty list), so the scrub cannot cover them. The rule: each organization publishes its own public repos from its own twin, with a login that can list that owner's private repos. Publish threejs's public repos from threejs's own twin, as a login that can list threejs's private repos.

Seats from another owner's repos join this workstream when their roster declares threejs in "workstream_owners"; (b) walks the same mechanism in the other direction.

(b) The Three.js maintainers join the egpt-frqtl workstream

The egpt-frqtl twin <owner>/<twin> is a private twin like the one in (a): its roster names DeSciX/egpt-frqtl in publishes_to and has one owner, <owner>. It masters workstream studio. The Three.js seats stay in their own twin, threejs/three.js-dev, and join studio because their roster declares <owner> in "workstream_owners". Workstream discovery searches the owners a roster names (repo, board, seat repos) plus its workstream_owners; an owner not declared is never searched. The master stays private: every write to it passes coord_write_guard.

Deferred, not yet supported: steps 2 to 5 act under the Three.js maintainers' own logins, in a repo another login owns. No run with a second login exists (Gap 1); these steps are described from the scripts. Steps 1, 6 and 7 run as <owner> alone.

  1. Open the workstream in the egpt-frqtl twin, as <owner>. The workstream's Project is created under --owner, and on a personal account only that user can create it. The owner also creates their own seat, which the publish in step 6 uses: 
    cd ~/code/egpt-frqtl-twin && ${CLAUDE_PLUGIN_ROOT}/scripts/workstream.sh new --slug studio --owner <owner> \
  --title "WS: STUDIO Three.js capabilities" --repo <owner>/<twin> \
  --northstar-file northstar.md \
  --milestone "M1 STUDIO capabilities|2026-11-30|Three.js features usable from STUDIO"
${CLAUDE_PLUGIN_ROOT}/scripts/seat.sh new LEAD --repo-path ~/code/egpt-frqtl-twin --agent daita-beast:seat --workstream studio
  2. Grant access (GitHub, not Beast; the owner's act). A joining seat writes the master's ## Seats table and CLAUDE.md block and records its address on the tracking issue, so each Three.js login needs write access to the twin: 
    gh api -X PUT repos/<owner>/<twin>/collaborators/alice-three
gh api -X PUT repos/<owner>/<twin>/collaborators/bob-three
    Each call sends an invitation; the access starts only when the invitee accepts it, on GitHub or with gh api user/repository_invitations (to find its id) and gh api -X PATCH user/repository_invitations/<id>. On a personal-account repo an accepted collaborator gets write access. The maintainers need no access to the public repo for this.
  3. Declare the owner in the Three.js roster. In threejs/three.js-dev's .beast/roster.json add, at the top level: 
    "workstream_owners": ["<owner>"]
    Commit it. The field is a list of GitHub owner names, each once, none of them an owner the roster already names; anything else stops every lookup, naming the field. Without it, seat.sh new … --workstream studio dies with no open issue labelled workstream and ws:studio among user:threejs: … a tracking issue under another owner is searched only when this roster's "workstream_owners" lists that owner.
  4. Each maintainer creates a seat in studio, from the Three.js checkout, logged in as themselves: 
    cd ~/code/three.js-dev && ${CLAUDE_PLUGIN_ROOT}/scripts/seat.sh new STUDIO --repo-path ~/code/three.js-dev --agent daita-beast:seat --workstream studio
    The roster row stays in threejs/three.js-dev; the seat appears in studio's ## Seats table on the twin's tracking issue. A login holds a label once per roster, so alice-three takes STUDIO beside her THREE seat in studio-scenes. The identity is studio/STUDIO/alice-three. Commit and push the roster, then /daita-beast:join studio/STUDIO/alice-three.
  5. Get a PR reviewed in the twin. The seat works on a branch of the twin and opens a PR on <owner>/<twin>, using the hand-back body: ## What, ## Evidence, ## Review against the engineering rules, ## Closes. The seat's own roster names a Three.js owner, so the request names the decider: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/pr.sh request <owner>/<twin>#42 --seat alice-three/STUDIO --assignee <owner> --milestone "M1 STUDIO capabilities"
    This labels the PR needs-review and seat:alice-three/STUDIO, assigns <owner> and posts the requesting seat's seen ack on the PR. The decider answers on the PR with approve, revise: … or reject: …. On approval the seat runs: 
    cd <home> && ${CLAUDE_PLUGIN_ROOT}/scripts/pr.sh close <owner>/<twin>#42 --merge --words "approve" --record https://github.com/<owner>/<twin>/pull/42#issuecomment-… --by alice-three/STUDIO --board <owner>/<twin>
    --record is the URL of the decider's answer comment, copied from the PR. --board names the board to republish; without it pr.sh close republishes the board of the closing seat's own roster.
  6. Publish to DeSciX/egpt-frqtl, as <owner>, from the twin's main checkout and the owner's seat <owner>/LEAD. The rule: each organization publishes its own public repos from its own twin, with a login that can list that owner's private repos. The twin's roster names <owner>, a personal account, so only <owner> can publish it; workstream_owners adds no owner to what a publish lists, so the Three.js seats change nothing here. 
    cd ~/code/egpt-frqtl-twin
${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh prepare studio-three --paths src/studio --message-file msg.txt
${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh request studio-three --seat <owner>/LEAD --body-file body.md --milestone "M1 STUDIO capabilities"
# the decider answers on the twin's approval row:  publish studio-three
${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh merge studio-three --words "publish studio-three" --by <owner>/LEAD
git -C ~/code/egpt-frqtl-twin push
    prepare builds exactly one new commit on the public main branch; the twin's history never travels. A scrub gate runs inside prepare, request and merge. It refuses private repo names, local paths, BEAST- lines, words from the twin's closed decisions, roster patterns and secret-shaped file names. If it finds anything it lists every hit and creates nothing.
  7. Bring public contributions back. In the twin's main checkout, with a clean tree: 
    ${CLAUDE_PLUGIN_ROOT}/scripts/publish.sh pull
    publish.sh merge refuses while the public main has commits the twin lacks, so pull first. If the pull conflicts it aborts, leaves main unchanged and names the files. A pull that merges ends by telling you to push the twin's main branch: pulled public … into twin …; push it: git push origin ends by telling you to push the twin's main: git push origin main.lt;branchends by telling you to push the twin's main: git push origin main.gt;.

egpt-godsworld follows the same pattern through its own private twin, which publishes to DeSciX/egpt-godsworld.

(c) Public developers

Outside developers never touch a twin. They fork and open an ordinary pull request on DeSciX/egpt-frqtl, DeSciX/egpt-godsworld or mrdoob/three.js. Beast puts no review machinery on public PRs: pr.sh refuses a public repo. A maintainer with write access on the public repo reviews and merges in GitHub, and the twin then runs publish.sh pull. Bounties and awards are allowed on public repos, and the public repo serves as the bulletin board. See Token rewards.

Gaps: what the hypothetical needs and 1.5.10 does not do

  1. Seats under a second GitHub login are not yet supported. The protocol says "Every seat posts as the decider's login today" (docs/protocol.md:115; pr.sh:6-8), and docs/design/adopting.md:88 says seats under a second GitHub login "are designed (the roster's github field differs, and GitHub would send its own notifications) but have not been run with a second login". Steps (a)3 and (b)2 to 5 are deferred until one is run.
  2. Beast has no command for granting access. Adding collaborators, creating the twin and creating the public repo are GitHub acts by the owner (plugin/skills/publish/SKILL.md:8: "creating it is its owner's act").
