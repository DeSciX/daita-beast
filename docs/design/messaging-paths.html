Beast messaging paths

How the decisions board, the relay and the seats talk; which connector each call goes through; and whose identity and money each call spends. As built in daita-beast 1.5.7; measurements taken 2026-10-20.

In short
  • Every Beast message and every board read goes through GitHub, as one GitHub user: the decider's login. The board page, the seats' scripts and the relay all draw on the same GitHub limits.
  • The DeSciX connector is not on the Beast path in 1.5. No Beast script, skill or page calls it, so DeSciX credits spent on the board are zero for every account. An earlier, platform-backed Beast plugin did call the DeSciX platform from every session start; it is retired.
  • The model cost sits on your Claude account. That covers the seat sessions, their builders, the relay's Haiku messenger and Cowork's republish. GitHub calls cost nothing in money. They cost quota.
  • The 403 was GitHub's secondary rate limit, which trips on bursts, not on totals. At the time the page fired 3 searches every 2 minutes. On top of that came its comment reads, the relay's searches, and the seats' scripts after the day's rejoins, all as the decider's login. The primary limits were far from full: right afterwards, search stood at 2 of 30 a minute and REST at 60 of 5,000 an hour.
  • Improvement options are a separate proposal, kept outside these as-built docs.

The interaction paths

Blue arrows are GitHub API calls. Orange are Claude model runs. Grey are local messages. There is no purple: no DeSciX call happens on this path.

One decision, end to end

  1. A seat files a row: decision.sh new creates an issue, as the decider's login via gh.
  2. The relay's next tick, at most 120 s later, runs one incremental search and diffs it against each seat's snapshot. On a change it starts one Haiku run, which SendMessages a BEAST-EVENT line to each seat with a fresh address.
  3. The board page finds the row through its own search on the claude.ai GitHub connector, and reads the row's comments.
  4. The decider answers on the page. The page posts one comment as the decider's login through the connector.
  5. The relay's next tick sees the comment and messages the seat. The seat acts, using gh as the decider's login, and acks with another comment.

Seat to seat, nothing goes through GitHub when both sessions share a Claude account and a machine and the address is fresh: it is one local SendMessage tagged BEAST-MSG … blocking=no. Otherwise the line goes to the recipient's desk issue as a comment.

Why the board hit the limit

What GitHub said: 403 "You have exceeded a secondary rate limit", on two searches, with "retry after 7s".

Secondary limits are burst limits. GitHub applies them to how many requests arrive close together, and searches weigh most. They are separate from the 30-a-minute search limit and the 5,000-an-hour REST limit, neither of which was close:

Who was searching as the decider's login around 17:15Z:

  • The page: three watches (open rows, decided rows, desks), each refetching every 2 minutes, plus one comment read per row on load. Its own retry asked the runtime to refetch every search at once, which is itself a burst.
  • The relay: an incremental search every 2 minutes, plus the workstream list.
  • The seats: all six seats rejoined after the 1.5 migration. Each join ran 17 searches until the 1.5 fix cut that to 5, and BEAST was filing, revising and publishing.

Measured from here: the search counts per join, the relay cadence, and the quota snapshot above. Not measured: whether the claude.ai connector's calls count in the same per-user buckets as gh. GitHub's documentation says a user's tokens share that user's limits. The two-minute test below settles it.

What 1.5.7 changes

  • The page makes one search for rows and desks together every 2 minutes. It refreshes the decided list every 15 minutes, or when you open that tab. Over a simulated 30 minutes the page made 48 search calls before and 19 now. That comparison is from a stubbed connector.
  • On a rate limit the page backs off. It waits at least 60 s, or what GitHub asks, and doubles the wait on each repeat. It shows one muted line, "GitHub asked the page to slow down; showing the list as of …", instead of red blocks.
  • Comments are read again only for rows whose updated_at moved.

Two-minute check you can run

  1. In a terminal, run gh api rate_limit --jq .resources.search and note used.
  2. Press Refresh on the board page twice.
  3. Run the command again within the same minute. If used went up by the page's searches, the connector and gh share the decider's login's search bucket. If it didn't, the connector has its own limit and the collisions came from the page alone.
